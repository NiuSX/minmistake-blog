# 应用三层存储架构学习文档

> 适用场景：Kotlin Multiplatform（Android + JVM/Desktop）应用中的数据持久化设计

---

## 一、整体架构总览

一个成熟的应用通常不会只用"一种"存储方式解决所有问题，而是根据数据的**读写频率、结构化程度、生命周期**，分层选择合适的存储介质：

```
📦 第一层：Res 资源（打包时的静态文件）
│  ├── 位置：APK/JAR 内部
│  ├── 操作：只读
│  └── 用途：图标、字体、固定配置

💾 第二层：DataStore（结构化配置存储）
│  ├── 位置：应用私有目录（Android: filesDir, JVM: 用户目录）
│  ├── 操作：读写结构化数据（JSON）
│  └── 用途：用户设置、Modbus配置、应用偏好

📁 第三层：FileStore（通用文件读写）
│  ├── 位置：应用私有目录或自定义路径
│  ├── 操作：任意文件读写（字符串/字节流）
│  └── 用途：工作流定义文件、日志、缓存、下载文件
```

这三层的核心区别可以用一句话概括：

> **Res 是"出厂设置"，DataStore 是"用户设置"，FileStore 是"用户数据"。**

---

## 二、三层详解

### 1. Res 资源层

| 维度 | 说明 |
|---|---|
| 本质 | 编译打包时被"冻结"进安装包的资源 |
| 位置 | Android 的 `res/` 或 `assets/`；JVM 的 classpath 资源（`resources/`） |
| 读写权限 | **只读**，运行时无法修改（除非重新打包发版） |
| 典型内容 | 图标、图片、字体、多语言字符串、默认配置模板 |
| 访问方式 | Android: `context.resources` / `assets`；Kotlin Multiplatform Compose Resources：`Res.drawable.xxx`、`Res.readBytes()` |
| 生命周期 | 与安装包版本绑定，卸载或更新即改变 |

**适用场景判断**：如果这份数据"每个用户看到的都一样、不会被用户修改、只在发版时才会变化"，就应该放在 Res 层。

---

### 2. DataStore 存储层（你现在所在的位置）

| 维度 | 说明 |
|---|---|
| 本质 | 面向**结构化配置**的键值/对象存储，通常序列化为 JSON |
| 位置 | 应用私有目录：Android 是 `filesDir`（沙盒目录），JVM/Desktop 一般放在用户主目录下的应用专属文件夹 |
| 读写权限 | 应用私有可读写，其他应用/进程无法直接访问 |
| 典型内容 | 用户偏好设置（主题、语言）、设备连接配置（如题目中的 Modbus 参数）、功能开关 |
| 数据特征 | 数据量小、结构固定、需要类型安全的读写 |
| 常见实现 | Android Jetpack `DataStore`（Preferences DataStore / Proto DataStore）；KMP 场景常用 `kotlinx.serialization` + 自定义 `Settings` 抽象（如 `multiplatform-settings` 库） |

**为什么不用 SharedPreferences？**
`DataStore` 是 Google 推荐替代 `SharedPreferences` 的方案，原因包括：
- 基于协程/Flow，天然支持异步和响应式监听
- 避免 `SharedPreferences` 的 ANR 风险（同步 IO 阻塞主线程的问题）
- Proto DataStore 支持强类型 schema，减少运行时类型错误

**Kotlin Multiplatform 中的典型设计（expect/actual 模式）**：

```kotlin
// commonMain
interface ConfigStore {
    suspend fun <T> save(key: String, value: T, serializer: KSerializer<T>)
    suspend fun <T> load(key: String, serializer: KSerializer<T>): T?
    fun <T> observe(key: String, serializer: KSerializer<T>): Flow<T?>
}

// androidMain: 基于 androidx.datastore.preferences 实现
// jvmMain: 基于本地 JSON 文件 + 自定义序列化实现（本质上是"披着 DataStore 外衣的轻量 FileStore"）
```

> **提示**：在很多跨平台项目里，JVM 端的 DataStore 底层其实就是"一个专门存配置的 JSON 文件"，只是在 API 设计上刻意与 FileStore 区分开，以强调"结构化配置"这个语义边界，而不是任意文件。

---

### 3. FileStore 通用文件层

| 维度 | 说明 |
|---|---|
| 本质 | 不关心内容结构，只负责"按路径存/取字节或字符串" |
| 位置 | 应用私有目录或用户指定的任意路径（需要处理权限） |
| 读写权限 | 完全读写，格式不限 |
| 典型内容 | 工作流定义 JSON/YAML 文件、运行日志、下载的附件、图片缓存、导出的报表 |
| 数据特征 | 数据量可大可小，结构不固定，可能需要用户手动管理（导入/导出/分享） |
| 常见 API | Android: `FileOutputStream` / `okio` / `java.io.File`；JVM: `java.nio.file.Path` + `Files` |

**FileStore 与 DataStore 的关键区别不是"能不能存 JSON"，而是语义定位**：

| 对比维度 | DataStore | FileStore |
|---|---|---|
| 谁在用这份数据 | 应用自己（内部配置） | 应用 + 可能被用户查看/导出/分享 |
| 是否有明确 Schema | 是，通常对应一个 Kotlin data class | 不一定，可能是任意格式文件 |
| 是否需要监听变化 | 常见需求（Flow 响应式） | 较少，多是一次性读写 |
| 典型大小 | KB 级 | KB 到 GB 级都有可能 |
| 举例 | "上次选择的 Modbus 端口号" | "用户导入的整个工作流定义文件" |

## 三、三层如何协同工作（以你的项目为例）

结合你之前展示的 `WorkflowReducer` 代码，可以推测一个典型的工作流引擎应用中，三层是这样配合的：

```
启动应用
   │
   ▼
① 从 Res 读取默认工作流模板 / 图标资源（只读，出厂自带）
   │
   ▼
② 从 DataStore 读取用户上次的配置
   （比如：默认执行超时时间、Modbus 连接参数、UI 主题）
   │
   ▼
③ 从 FileStore 读取用户创建/导入的工作流定义文件（.json）
   │
   ▼
   构造 WorkflowExecutionState，交给 WorkflowReducer 处理事件
   │
   ▼
运行过程中产生的日志、执行结果 → 写回 FileStore（可导出/查看）
运行过程中用户修改的偏好设置 → 写回 DataStore（自动持久化）
```

一句话总结职责边界：

- **Res**：程序"天生就有"的东西
- **DataStore**：程序"记住你怎么用它"的东西
- **FileStore**：用户"自己创造或产生"的东西

## 四、常见误区与最佳实践

1. **不要用 FileStore 存零散的配置项**
   如果为每个开关、每个参数都单独建一个文件，会导致 IO 频繁、难以维护。这类数据应该聚合进 DataStore 的一个结构化对象里。

2. **不要用 DataStore 存大文件或非结构化数据**
   DataStore 设计初衷是小型配置，硬塞入大 JSON 或二进制数据会拖慢序列化/反序列化性能。

3. **Res 资源不要在运行时"模拟可写"**
   有些团队会尝试把默认配置模板放进 Res，然后"复制一份到 FileStore 再修改"，这是正确做法；但如果尝试直接修改 Res 内容，在大多数平台上是不可行的（打包后不可变）。

4. **跨平台项目中优先用 expect/actual 或接口抽象统一三层的调用方式**
   让 `commonMain` 中的业务逻辑（比如 `WorkflowReducer`、`ExecutionService`）完全不感知底层是 Android 还是 JVM 实现，只依赖 `ConfigStore` / `FileStore` 接口。

5. **权限与沙盒边界要提前设计**
   尤其是 Android，`filesDir` 之外的路径需要处理运行时权限（如 `MANAGE_EXTERNAL_STORAGE`），JVM 端则要注意跨用户/跨系统的路径兼容性（`System.getProperty("user.home")` 等）。

## 五、快速判断口诀

遇到一份新数据不知道该放哪一层时，可以按顺序自问：

1. **这份数据会随版本发布变化，但运行时不会被修改吗？** → 放 **Res**
2. **这份数据是一个不大的、结构固定的配置对象，需要被程序自动记住吗？** → 放 **DataStore**
3. **除此之外的一切（尤其是用户自己产生、可能很大、格式不固定的数据）** → 放 **FileStore**
