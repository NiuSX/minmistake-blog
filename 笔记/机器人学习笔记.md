## 1. 先建立机器人系统观

### 1.1 机器人本质上是一个闭环系统

一个可工作的机器人通常包含以下闭环：

```text
环境
  ↓
传感器：编码器、IMU、LiDAR、相机、力传感器
  ↓
状态估计：里程计、TF、定位、传感器融合
  ↓
环境理解：地图、点云、目标、代价地图
  ↓
规划：任务规划、全局路径、局部轨迹
  ↓
控制：速度、关节轨迹、电机电流
  ↓
执行机构：底盘、机械臂、夹爪
  ↓
新的传感器观测和反馈
```

机器人不是“把一个算法接上去”就完成了。模型错误会导致 TF 和碰撞检测错误，时间戳错误会导致传感器融合发散，控制频率不足会导致轨迹跟踪抖动，地图或 footprint 错误会导致导航规划穿墙，缺少故障处理则可能使系统在传感器失联后继续运动。

### 1.2 用输入、输出和边界理解每个模块

学习任何模块时，建议写下以下七项：

| 项目 | 需要回答的问题 |
|---|---|
| 输入 | 订阅了哪些 Topic、Service、Action 或参数？ |
| 输出 | 发布了什么数据或控制命令？ |
| 坐标系 | 消息中的 `frame_id` 是什么？输入输出是否需要 TF？ |
| 时间 | 使用消息时间、系统时间还是仿真时间？允许多大延迟？ |
| 频率 | 传感器、估计器、规划器和控制器分别以多少 Hz 运行？ |
| 约束 | 速度、加速度、关节限位、碰撞、通信和安全约束是什么？ |
| 验收 | 如何通过日志、曲线、误差和场景测试判断它工作正常？ |

### 1.3 机器人知识地图

| 层次 | 核心内容 | 典型产物 |
|---|---|---|
| 数学 | 线性代数、概率、微积分、优化 | 变换、滤波、代价函数 |
| 机器人学 | 刚体运动、运动学、动力学、控制 | FK、IK、Jacobian、PID |
| 中间件 | ROS 2 节点、通信、参数、启动、生命周期 | 可组合的软件模块 |
| 建模 | URDF、Xacro、SDF、惯性、碰撞、传动 | 可视化和仿真模型 |
| 感知 | LiDAR、相机、IMU、标定、时间同步 | 可信的传感器数据 |
| 估计 | 里程计、EKF/UKF、定位、SLAM | 连续、平滑的机器人状态 |
| 规划 | 全局规划、局部控制、行为树、恢复 | 可执行的路径和任务 |
| 仿真 | Gazebo、ros2_control、传感器噪声 | 可重复的测试场景 |
| 工程 | 安全、日志、回归、部署、运维 | 可交付、可复现的系统 |

### 1.4 用五层架构定位问题

面对一个“机器人不能正常工作”的问题，先判断它属于哪一层。不同层的问题，观测信号和修复方法完全不同。

| 层次 | 主要职责 | 典型问题 | 首要观测 |
|---|---|---|---|
| 设备层 | 电机、驱动器、电池、传感器和通信总线 | 电机不使能、编码器方向反、设备掉线 | 电流、温度、错误码、串口/CAN 日志 |
| 运动层 | 里程计、运动学、关节控制和底盘控制 | 直行偏移、旋转角度不准、轨迹跟踪抖动 | 实际速度、编码器、`/odom`、控制频率 |
| 感知层 | 激光、相机、IMU、点云和目标检测 | 点云错位、图像延迟、传感器数据为空 | Topic、QoS、`frame_id`、时间戳、频率 |
| 认知层 | 定位、SLAM、地图、规划和行为树 | 定位漂移、规划失败、恢复行为循环 | TF、地图、代价地图、路径和状态 |
| 应用层 | 任务流程、调度、交互和业务逻辑 | 任务状态混乱、取消无效、异常后不恢复 | Action 反馈、状态机、任务日志、诊断 |

排错时要遵循“从下到上”的顺序。例如导航失败时，不要先修改规划器权重；先确认底盘能够执行速度、里程计方向正确、传感器数据和 TF 可用，再进入地图、代价地图和规划器层。

### 1.5 从传感器到执行器的数据流

以“移动机器人前往目标点”为例，可以把系统拆成一条可观测的数据链：

```text
用户目标
  ↓ NavigateToPose Action
任务/行为树
  ↓ 目标位姿、反馈、取消和恢复
定位模块
  ↓ map -> odom
状态估计器
  ↓ odom -> base_link、速度和协方差
传感器与代价地图
  ↓ LaserScan/PointCloud2/Map
全局规划器
  ↓ 全局路径
局部控制器
  ↓ cmd_vel
底盘控制器
  ↓ 轮速或电机命令
电机与机器人本体
  ↓ 编码器和 IMU
里程计与诊断反馈
```

这条链路中的每个箭头都可能成为故障边界。建议为关键箭头建立最小检查问题：

| 数据边界 | 最小检查问题 |
|---|---|
| 目标 → 行为树 | Action 是否收到目标？反馈和取消是否生效？ |
| 定位 → TF | 是否存在正确时间的 `map -> odom`？ |
| 估计 → 控制 | `odom` 是否连续？速度、协方差和方向是否合理？ |
| 传感器 → costmap | 障碍是否进入正确 frame，是否按预期清除？ |
| 控制器 → 底盘 | `/cmd_vel` 是否被订阅、限幅和执行？ |
| 底盘 → 反馈 | 实际速度是否跟随命令，编码器是否正常变化？ |

### 1.6 开环、闭环和自治的区别

**开环**只发送命令，不根据结果修正。例如固定时间向左转两秒。开环结构简单，但无法抵抗电池电压、地面摩擦、负载和通信延迟的变化。

**闭环**会比较目标与反馈，根据误差持续修正。例如使用编码器反馈控制轮速，使用定位反馈修正导航轨迹。闭环并不意味着一定正确，反馈本身可能有延迟、噪声、错误坐标或错误符号。

**自治**是在闭环之上增加环境理解、任务决策和异常处理。一个自治系统不仅要“能到达”，还要能判断定位质量、避开障碍、取消任务、进入恢复状态并在无法保证安全时停止。

| 结构 | 是否使用反馈 | 能否处理扰动 | 典型用途 |
|---|---:|---:|---|
| 开环 | 否 | 很弱 | 简单执行、初步硬件测试 |
| 闭环 | 是 | 较强 | 速度控制、姿态控制、轨迹跟踪 |
| 自治闭环 | 是，并包含任务决策 | 需要处理环境和故障 | 导航、巡检、配送、抓取 |

### 1.7 学习一项技术的六步法

不要只从“安装命令”开始。建议每个主题都按以下顺序学习：

1. **先说清用途**：它解决的是感知、估计、规划、控制还是任务问题？
2. **画出接口**：列出输入输出、消息类型、Topic、TF、参数和启动关系。
3. **确认约束**：记录单位、坐标系、时间戳、频率、延迟、限幅和失败条件。
4. **做最小实验**：只启用一个传感器、一个节点或一条运动链路。
5. **制造故障**：主动断开 Topic、修改 frame、降低频率、加入噪声或触发取消。
6. **形成验收记录**：保留命令、参数、截图、bag、指标和问题结论。

以 TF 为例，不能只记住 `map`、`odom` 和 `base_link` 的名称；还要验证谁发布它们、发布频率是多少、查询历史时间是否成功、机器人运动时方向是否符合预期，以及断开定位节点后系统应该如何降级。

### 1.8 第一阶段的最小闭环项目

初学者可以先完成一个不依赖复杂算法的差速小车闭环：

```text
键盘或脚本发布 /cmd_vel
        ↓
差速底盘控制器
        ↓
轮速和编码器反馈
        ↓
/odom 与 odom -> base_link
        ↓
RViz2 显示 RobotModel 和轨迹
```

建议按以下任务递进：

| 任务 | 实现内容 | 验收标准 |
|---|---|---|
| 任务一 | 发布固定线速度和角速度 | 能安全启动、停止和限速 |
| 任务二 | 根据左右轮速度计算里程计 | 直行方向、旋转方向和单位正确 |
| 任务三 | 发布 `odom -> base_link` | RViz2 中模型和轨迹连续 |
| 任务四 | 加入 LiDAR 和静态 TF | 激光点与机器人模型位置一致 |
| 任务五 | 记录并回放 rosbag2 | 离线能够复现运动和诊断数据 |
| 任务六 | 注入传感器或通信故障 | 超时后停止或进入明确降级状态 |

第一阶段不建议同时加入 SLAM、Nav2、视觉检测和复杂行为树。最小闭环的价值在于：每条数据链路都能解释，出现问题时能快速定位到设备、运动、感知或软件接口。

### 1.9 机器人系统的三个核心不变量

长期学习和调试时，可以把以下三条当作系统不变量：

1. **空间一致**：每条数据都能回答“在哪个坐标系中”，并且变换方向和单位正确。
2. **时间一致**：每条数据都能回答“在什么时候采集”，不同模块对仿真时间、延迟和缓存的理解一致。
3. **行为可控**：每个控制输出都受到速度、加速度、碰撞、通信和安全状态约束，故障时有明确的停止或降级动作。

如果一个现象无法解释，优先检查这三个不变量，而不是马上更换算法。很多看似复杂的导航、SLAM 或控制问题，最后都可以归结为坐标、时间或约束没有被正确实现。

### 1.10 第一章自测清单

读完本章后，应该能够不看资料回答：

- 为什么机器人必须同时关注模型、传感器、估计、规划和控制？
- `map`、`odom`、`base_link` 各自承担什么职责？
- `/cmd_vel` 发布了但机器人不动时，应该按照什么顺序排查？
- 为什么 QoS、时间戳和 `frame_id` 会导致“Topic 存在但数据不可用”？
- 开环、闭环和自治系统有什么区别？
- 为什么要先做最小差速底盘闭环，再学习 SLAM 和 Nav2？
- 一个机器人功能至少需要记录哪些输入、输出、约束和验收指标？

本章的最终产物不是一张概念图，而是一份可以执行的系统说明：画出数据流，列出接口和坐标系，标注时间与频率，写明成功与失败条件，并用一个最小项目验证它。

## 2. 学习前的基础与环境

### 2.1 必备基础

1. **Linux**：进程、权限、网络、环境变量、`systemd`、日志和 Shell 脚本。
2. **C++ 或 Python**：至少能编写 ROS 2 Publisher、Subscriber、Action Client 和参数化节点。
3. **线性代数**：向量、矩阵、逆矩阵、特征值、齐次变换和坐标变换。
4. **概率与微积分**：高斯分布、协方差、贝叶斯更新、导数和梯度。
5. **Git**：分支、提交、差异、回滚和子模块。
6. **电机与传感器常识**：编码器、IMU、串口、CAN、Ethernet、轮速和采样频率。

### 2.2 ROS 2 发行版选择

学习时不要把“最新文档”和“项目实际发行版”混为一谈。先在项目 README、容器镜像或机器人设备上确认 ROS 2 发行版，再固定对应版本的文档和依赖。个人学习可优先选择仍受支持的 LTS 发行版，例如 Jazzy；需要使用最新特性时再评估 Kilted 或更新发行版。

建议记录：

```bash
printenv ROS_DISTRO
ros2 doctor --report
uname -a
lsb_release -a
```

同一个工作空间不要混用不同发行版的 `/opt/ros/<distro>` 环境。新终端应明确执行：

```bash
source /opt/ros/$ROS_DISTRO/setup.bash
source install/setup.bash
```

### 2.3 工作空间和包

ROS 2 工作空间通常包含 `src/`、`build/`、`install/` 和 `log/`：

```text
ros2_ws/
├── src/       # 源码、消息、启动文件、参数
├── build/     # 构建中间产物
├── install/   # 安装结果和环境入口
└── log/       # 构建与运行日志
```

推荐先建立一个最小包，而不是一开始复制完整机器人仓库：

```bash
mkdir -p ~/ros2_ws/src
cd ~/ros2_ws/src
ros2 pkg create --build-type ament_cmake robot_bringup
cd ~/ros2_ws
colcon build --symlink-install
source install/setup.bash
```

`--symlink-install` 适合开发阶段，修改 Python、配置和部分资源时可以减少重复复制；发布或 CI 验证仍应执行干净构建。

### 2.4 学习环境、开发环境与部署环境

机器人项目通常至少有三套环境，不应把它们混为一谈：

| 环境 | 目标 | 主要特点 |
|---|---|---|
| 学习环境 | 快速理解概念和验证小实验 | 可以使用桌面版工具，允许频繁重装和清理 |
| 开发环境 | 编写节点、调试参数和联调 | 需要编译工具、调试器、仿真器和版本控制 |
| 部署环境 | 在机器人上稳定运行 | 依赖固定、权限收敛、日志可追踪、启动可恢复 |

学习阶段可以追求便利，但进入项目后必须记录操作系统、ROS 2 发行版、编译器、Python、Gazebo、驱动和关键库版本。一个“在我电脑上能跑”的实验，如果没有版本和参数记录，通常无法迁移到同事电脑、CI 或真机。

建议在项目根目录维护一份环境清单：

```text
环境名称：
操作系统及版本：
ROS 2 发行版：
RMW 实现：
编译器：
Python 版本：
Gazebo/仿真器版本：
显卡驱动和 CUDA：
硬件型号与固件：
代码提交号：
地图、模型和参数版本：
```

### 2.5 安装方式的选择

#### 二进制安装

适合初学、快速运行官方教程和验证常用包。优点是安装简单、依赖已经打包；缺点是版本由发行版固定，源码级修改和最新功能需要另外建立工作空间。

#### 源码安装

适合需要修改 ROS 2 包、跟踪上游问题、使用尚未发布功能或参与项目开发的场景。源码安装必须同时管理依赖版本、构建顺序和补丁，不建议在没有版本记录的情况下把源码包直接覆盖系统安装。

#### 容器安装

适合固定构建环境、CI 和多人协作。容器不能自动解决硬件访问、GUI、GPU、网络发现和 USB/CAN 权限问题；运行机器人驱动时，仍需要明确映射设备、网络和时钟。

#### 真机安装

真机环境首先满足安全和可恢复性，再追求功能数量。不要在机器人正在运行任务时随意升级系统、切换 ROS 2 发行版或删除工作空间。升级前至少备份代码、参数、地图、模型、固件和回滚方案。

### 2.6 Shell 环境与 `source` 顺序

ROS 2 的命令能否找到，取决于当前 Shell 的环境变量。推荐按“系统 ROS 2 → 工作空间 overlay”的顺序加载：

```bash
source /opt/ros/jazzy/setup.bash
source ~/ros2_ws/install/setup.bash
```

验证当前环境：

```bash
echo "$ROS_DISTRO"
echo "$AMENT_PREFIX_PATH"
echo "$COLCON_PREFIX_PATH"
which ros2
ros2 pkg prefix rclcpp
```

常见原则：

- 只在确认发行版后，才把 `source /opt/ros/.../setup.bash` 写入 `~/.bashrc`。
- 新工作空间构建前，先 source 它依赖的底层工作空间。
- 切换发行版时打开新终端，或主动清理旧的 `AMENT_PREFIX_PATH` 等变量。
- 工作空间中的包覆盖同名系统包时，要确认覆盖是有意的。
- 运行 `ros2`、`colcon` 和节点的终端，必须使用同一套环境。

如果出现“包明明存在但找不到”，优先检查 `which ros2`、`ros2 pkg prefix <package>` 和当前 Shell 的 source 顺序，不要先删除代码。

### 2.7 推荐的 ROS 2 包结构

一个可维护的包应让源码、启动文件、参数和资源有清晰边界：

```text
robot_base/
├── package.xml          # 包名、版本、依赖和导出信息
├── CMakeLists.txt       # C++ 编译和安装规则
├── include/robot_base/  # C++ 头文件
├── src/                 # C++ 源文件
├── robot_base/          # Python 模块和可执行入口
├── launch/              # launch.py 或 launch.xml
├── config/              # YAML 参数
├── rviz/                # RViz2 配置
├── urdf/                # URDF/Xacro
├── meshes/              # visual/collision 网格
├── test/                # 单元测试和集成测试
└── README.md            # 安装、运行、接口和验收说明
```

不要把所有代码都放到 `scripts/`，也不要把运行时生成的地图、bag、日志和构建产物提交到源码仓库。包的 README 至少说明：

1. 依赖哪些 ROS 2 包和系统库。
2. 如何构建和 source。
3. 如何启动节点或 launch。
4. 订阅和发布哪些 Topic、Service、Action。
5. 参数的单位、范围、默认值和覆盖方式。
6. 如何验证成功，以及已知限制是什么。

### 2.8 依赖声明与构建

`package.xml` 描述包的元数据和依赖，`CMakeLists.txt` 或 Python 打包配置描述构建和安装。依赖不能只存在于开发者电脑上，否则干净环境和 CI 会失败。

常用构建命令：

```bash
cd ~/ros2_ws
rosdep install --from-paths src --ignore-src -r -y
colcon build --symlink-install
source install/setup.bash
```

针对单个包快速验证：

```bash
colcon build --packages-select robot_base --symlink-install
colcon test --packages-select robot_base
colcon test-result --verbose
```

遇到构建问题时，按以下顺序定位：

1. 包是否被 `colcon list` 发现。
2. `package.xml` 是否声明了直接依赖。
3. C++ 头文件和链接库是否同时配置。
4. Python 入口是否安装到 `lib/<package>` 或正确的脚本路径。
5. launch、YAML、URDF 等资源是否写入 `install()` 规则。
6. 是否是旧的 `build/`、`install/` 或 `log/` 缓存造成的假象。

必要时执行干净构建：

```bash
rm -rf build install log
colcon build --symlink-install
```

清理操作只能针对当前工作空间，不能把系统 `/opt/ros/<distro>` 当成缓存删除。

### 2.9 C++、Python 和混合开发的选择

| 场景 | 优先选择 | 原因 |
|---|---|---|
| 教程、工具、数据处理、快速原型 | Python / `rclpy` | 迭代快，代码短，便于实验 |
| 高频控制、硬件驱动、性能敏感节点 | C++ / `rclcpp` | 更好的性能、类型约束和资源控制 |
| 算法验证后需要产品化 | Python 起步，按瓶颈迁移 C++ | 先确认算法，再优化关键路径 |
| 自定义接口和跨语言通信 | `msg`/`srv`/`action` | 让 C++ 和 Python 共享明确契约 |

无论使用哪种语言，都要避免在回调中执行不可控的长时间阻塞任务。长任务应使用 Action、定时器、执行器或后台线程，并明确取消、超时和异常处理。

| 仿真时间不前进 | `/clock`、`use_sim_time` | 确认仿真器发布时钟且节点统一使用 |

## 3. ROS 2 核心：把通信图读懂

### 3.1 Node、Topic、Service、Action 和 Parameter

| 机制 | 适合场景 | 特征 |
|---|---|---|
| Node | 功能边界 | 一个进程可以有一个或多个节点 |
| Topic | 连续数据流 | 发布/订阅、异步、多对多 |
| Service | 短请求短响应 | 不适合长时间任务 |
| Action | 长时间、可反馈任务 | 支持反馈、结果和取消 |
| Parameter | 节点配置 | 应明确默认值、范围和单位 |
| TF2 | 带时间的坐标变换 | 维护坐标树和历史缓存 |

例如移动导航通常不是直接向 `/cmd_vel` 写一个目标点，而是通过 `NavigateToPose` Action 发送目标；Nav2 内部再由行为树协调定位、规划、控制和恢复。短操作可使用 Service，连续传感器数据使用 Topic，长任务必须考虑反馈和取消。

### 3.2 常用 CLI

```bash
ros2 node list
ros2 node info /node_name
ros2 topic list -t
ros2 topic info /scan --verbose
ros2 topic echo /odom --once
ros2 topic hz /scan
ros2 topic bw /camera/image_raw
ros2 interface show geometry_msgs/msg/Twist
ros2 service list -t
ros2 action list -t
ros2 param list /node_name
ros2 param dump /node_name
ros2 run tf2_tools view_frames
ros2 run tf2_ros tf2_echo odom base_link
```

排查时先用 `list` 确认对象存在，再用 `info` 确认连接和 QoS，最后用 `echo`、`hz`、`tf2_echo` 检查内容、频率和时序。只看到 Topic 名称并不等于数据可用。

### 3.3 QoS：数据存在但收不到的常见原因

ROS 2 的通信质量由 QoS 决定，关键策略包括：

- `reliability`：`reliable` 追求可靠传输，`best_effort` 允许丢包但延迟更低。
- `durability`：`volatile` 只接收订阅后的数据，`transient_local` 可让后加入的订阅者获得发布者保存的最近数据。
- `history`：`keep_last` 保存固定深度，`keep_all` 尽可能保留全部消息。
- `depth`：队列深度；太小会丢弃旧数据，太大则可能增加延迟和内存。
- `deadline`、`liveliness`、`lifespan`：用于检测周期、存活状态和消息有效期。

典型经验：传感器图像和点云常使用 `best_effort` 以降低延迟，地图或状态类数据可能需要 `reliable` 与 `transient_local`。最终不能凭经验猜，必须比较发布者和订阅者的实际 QoS：

```bash
ros2 topic info /scan --verbose
```

### 3.4 Launch、参数和生命周期

`launch` 负责描述系统启动关系，YAML 负责参数，生命周期节点负责从未配置到激活的确定性转换。大型机器人应把启动拆成层次：

```text
description.launch.py
├── robot_state_publisher
├── joint_state_broadcaster
└── static_transform_publisher

sensors.launch.py
├── lidar_driver
├── camera_driver
└── imu_driver

localization.launch.py
├── ekf_filter_node
├── slam_toolbox 或 amcl
└── map_server

navigation.launch.py
├── planner_server
├── controller_server
├── behavior_server
├── bt_navigator
└── lifecycle_manager
```

启动文件应尽量做到：可重复、可覆盖参数、可选择仿真/真机、可显式传入地图和命名空间。不要把所有节点和所有参数堆在一个不可维护的启动文件中。

### 3.5 ROS 2 通信图与分层架构

ROS 2 系统可以从三个角度理解：

```text
应用节点：任务、导航、感知、控制
        ↓ rclpy / rclcpp
客户端库：创建节点、发布订阅、定时器、参数、Action
        ↓ RMW
ROS Middleware：对接 DDS 或其他通信实现
        ↓
网络发现、序列化、传输、QoS 和数据分发
```

运行时通信图则由节点和接口组成：

```text
/camera_driver ── /image_raw ──> /detector
/lidar_driver  ── /scan ───────> /slam_toolbox
/wheel_driver  ── /odom ───────> /ekf_filter_node
/ekf_filter_node ── /tf ───────> /nav2_controller
/nav2_controller ── /cmd_vel ──> /base_controller
```

设计通信图时，先按职责划分节点，再决定接口类型。不要为了“少写几个节点”把驱动、估计、规划和控制全部塞进一个大节点；也不要为了“模块化”把每一行逻辑都拆成独立进程。合理边界应该同时考虑职责、故障隔离、频率、资源消耗和部署方式。

### 3.6 Topic、Service、Action 的选择原则

可以用“数据是否连续、任务是否耗时、调用方是否需要反馈”来选择接口：

| 问题 | 推荐接口 | 示例 |
|---|---|---|
| 数据会持续产生吗？ | Topic | `/scan`、`/odom`、`/joint_states` |
| 只是一次短请求吗？ | Service | 清空代价地图、查询状态、切换模式 |
| 任务可能持续较久吗？ | Action | 导航到目标、机械臂执行轨迹、抓取任务 |
| 是否需要配置而非运行时消息？ | Parameter | 速度上限、传感器 frame、算法权重 |

不要用 Service 传输高频数据，也不要用 Topic 模拟没有反馈和取消机制的长任务。Action 的客户端至少要处理目标是否接受、反馈是否更新、结果是否成功、任务是否取消和服务器是否失联。

### 3.7 消息契约：类型、Header、单位和语义

ROS 2 消息不仅是字段集合，还包含使用约定。设计或使用消息时至少确认：

1. 消息类型是否正确，例如 `sensor_msgs/msg/LaserScan` 和 `sensor_msgs/msg/PointCloud2` 不能混用。
2. `Header.stamp` 表示采集时间、计算时间还是发布时间。
3. `Header.frame_id` 指向哪个坐标系，是否能通过 TF 查询。
4. 数值单位是米、弧度、米每秒还是其他单位。
5. 空数组、NaN、Inf、无效值和超时应该如何解释。
6. 消息频率、队列深度和延迟是否满足订阅者要求。

查看消息定义和实际数据：

```bash
ros2 interface show nav_msgs/msg/Odometry
ros2 interface show sensor_msgs/msg/LaserScan
ros2 topic type /odom
ros2 topic echo /odom --once
```

`Odometry` 中的位姿和速度还带有协方差。不要只读取位置字段而忽略协方差、frame 关系和时间戳；估计器和导航模块可能依赖这些信息判断数据可信度。

### 3.8 命名、命名空间与重映射

机器人系统通常需要同时运行多个相同类型的设备，例如两台相机、多个底盘或多台机器人。命名空间可以避免 Topic 和参数互相覆盖：

```text
/robot_a/scan
/robot_a/cmd_vel
/robot_a/odom

/robot_b/scan
/robot_b/cmd_vel
/robot_b/odom
```

设计命名时建议：

- 使用表达职责的稳定名称，不把临时调试信息写进公共接口。
- 统一使用小写、下划线和清晰的层级结构。
- 用 namespace 区分机器人实例，用 remapping 适配不同硬件驱动。
- 记录相对名称和绝对名称，避免 launch 嵌套后路径意外变化。
- 参数名称、Topic 名称和 TF frame 名称不要只靠约定猜测。

启动时可重映射接口：

```bash
ros2 run demo_nodes_cpp talker --ros-args \
  -r chatter:=robot_a/status
```

重映射可以适配接口，但不能掩盖消息语义不一致。将 `/scan` 重映射到一个并非 `LaserScan` 的 Topic，只会把错误延迟到运行时。

### 3.9 参数设计与配置覆盖

参数应描述节点行为，而不是作为任意全局变量使用。每个参数都应明确：

| 参数信息 | 示例 |
|---|---|
| 类型 | `double`、`integer`、`boolean`、字符串或数组 |
| 单位 | 米、弧度、Hz、秒、米每秒 |
| 默认值 | 节点在最小配置下的安全行为 |
| 合法范围 | 最小值、最大值、是否允许零 |
| 修改时机 | 启动时读取，还是允许运行时修改 |
| 失败处理 | 参数无效时拒绝启动还是使用安全默认值 |

YAML 参数文件示例：

```yaml
controller_node:
  ros__parameters:
    control_frequency: 20.0
    max_linear_velocity: 0.5
    max_angular_velocity: 1.0
    use_sim_time: false
```

运行时检查和覆盖：

```bash
ros2 param list /controller_node
ros2 param get /controller_node max_linear_velocity
ros2 param set /controller_node max_linear_velocity 0.2
ros2 param dump /controller_node
```

修改参数后必须确认节点真的支持动态更新。控制器、传感器驱动和生命周期节点可能只在配置阶段读取参数；如果参数不能运行时修改，就应重启或重新配置节点，不要假设 `param set` 一定会改变行为。

### 3.10 执行器、回调和阻塞问题

ROS 2 节点中的订阅回调、定时器、Service 和 Action 回调由执行器调度。常见设计选择如下：

- 单线程执行器结构简单，适合回调短、资源少的节点。
- 多线程执行器适合多个独立回调并行，但必须保护共享状态。
- Callback Group 用于声明哪些回调可以并行、哪些回调必须互斥。
- 长时间计算、文件 I/O、网络访问和等待硬件不能无限阻塞主回调线程。

典型错误是：在一个订阅回调里同步等待另一个 Service 或 Action 的结果，导致执行器无法处理完成响应，形成死锁或超时。改进方式包括使用异步客户端、拆分状态机、增加合适的回调组，或把耗时任务放入明确管理的后台线程。

### 3.11 日志、诊断和故障上下文

日志不应只是“打印变量”。一条有用的日志至少包含事件、节点、状态、关键参数和可操作的下一步：

```text
[WARN] /lidar_driver: scan timeout, elapsed=0.42s, expected_period=0.10s, action=stop_navigation
```

建议区分日志等级：

- `DEBUG`：开发阶段的详细数据，不应无限输出。
- `INFO`：启动、配置、模式切换和正常任务进展。
- `WARN`：暂时可恢复的异常、超时和降级。
- `ERROR`：当前功能失败，需要处理或重试。
- `FATAL`：无法继续运行，通常需要停止并人工介入。

避免在高频传感器回调中每次都打印完整消息，这会造成 I/O 堵塞和日志膨胀。应使用节流、统计计数和摘要信息：

```bash
ros2 run rqt_console rqt_console
ros2 topic echo /diagnostics
ros2 topic echo /rosout --once
```

### 3.12 QoS 的实际排查流程

当“Topic 能看到但收不到消息”时，按以下顺序操作：

1. 确认发布者和订阅者是否真的存在。
2. 确认双方消息类型一致。
3. 使用 `ros2 topic info <topic> --verbose` 查看双方 QoS。
4. 比较 `reliability`、`durability`、`history` 和 `depth`。
5. 检查 namespace、remapping 和 ROS_DOMAIN_ID。
6. 检查消息时间戳和节点是否使用同一时钟。
7. 观察网络、防火墙、RMW 实现和 CPU 负载。

不要一看到 QoS 问题就把所有策略改成 `reliable`。可靠传输可能增加延迟和资源消耗，传感器数据还可能因为发布者和订阅者策略不兼容而完全无法匹配。正确做法是理解数据的实时性、丢包容忍度和是否需要历史数据，再选择策略。

### 3.13 Lifecycle、Composition 与系统启动顺序

普通节点通常启动后立即创建资源并开始工作；Lifecycle Node 则把过程拆成 `unconfigured`、`inactive`、`active` 和 `finalized` 等阶段。大型机器人使用生命周期可以让系统按顺序完成：

```text
创建节点
  → configure：读取参数、打开设备、创建资源
  → activate：开始发布数据和执行控制
  → deactivate：停止输出但保留资源
  → cleanup：释放资源
```

这对于 Nav2、传感器驱动和控制器尤其重要：节点已经存在，不代表它已经 active；active 也不代表传感器、TF 和控制反馈都正常。

Composition 可以把多个节点加载到同一进程，减少序列化和进程通信开销，适合高带宽图像和点云链路。但组件化会降低进程隔离程度，某个组件崩溃可能影响同一容器内的其他组件。是否使用 Composition，应根据性能、故障隔离、部署和调试成本决定。

### 3.14 最小 ROS 2 通信实验

用两个节点建立一条最小消息链：发布者周期性发布字符串，订阅者接收并记录时间。实验目标不是业务功能，而是验证节点发现、Topic 类型、QoS、参数和日志。

```text
/talker
  └── /chatter: std_msgs/msg/String
                    ↓
/listener
```

验收步骤：

```bash
ros2 node list
ros2 topic list -t
ros2 topic info /chatter --verbose
ros2 topic hz /chatter
ros2 topic echo /chatter --once
```

然后依次制造故障：

- 关闭发布者，观察订阅者行为。
- 修改 Topic 名称，确认通信断开并能通过 remap 恢复。
- 修改 QoS，记录何时发生不匹配。
- 改变发布频率，观察 `topic hz` 和队列行为。
- 将两个终端设置为不同 `ROS_DOMAIN_ID`，观察发现隔离。

### 3.15 第三章学习验收

完成本章后，至少应能够：

- 画出一个机器人系统的节点、Topic、Service、Action、参数和 TF 关系图。
- 根据数据是否连续、任务是否耗时和是否需要反馈选择通信机制。
- 解释消息的类型、单位、`Header.stamp` 和 `frame_id`。
- 使用 CLI 查看节点、接口、连接、频率、带宽、QoS、参数和 Action。
- 使用 namespace 和 remapping 同时运行多个机器人实例。
- 说明执行器、回调组、阻塞调用和多线程并发之间的关系。
- 为节点设计参数、日志、生命周期和失败处理。
- 用一个最小实验复现并解释 Topic、QoS、域 ID 和时间问题。

第三章的交付物应包括：一张 ROS 2 通信图、一份 Topic/Service/Action 接口表、一个参数 YAML、一次 QoS 排查记录，以及一段包含启动、观察、故障注入和恢复结果的实验日志。

## 4. 数学、坐标系与时间

### 4.1 刚体变换

三维刚体位姿可以用齐次变换表示：

\[
T = \begin{bmatrix} R & t \\ 0 & 1 \end{bmatrix},
\qquad p_A = T_{AB}p_B
\]

其中 `R` 是旋转矩阵，`t` 是平移向量。若需要把点从坐标系 `B` 转到 `A`，要确认变换的方向，而不是只看两个 frame 的名称。复合变换遵循矩阵乘法顺序：

\[
T_{AC}=T_{AB}T_{BC}
\]

### 4.2 旋转表示

常见表示有欧拉角、旋转矩阵、轴角和四元数：

- 欧拉角直观，但存在万向节锁，并且旋转顺序会改变结果。
- 旋转矩阵适合计算，需保持正交性。
- 四元数适合插值和 ROS 2 消息传输，但要注意归一化和乘法顺序。
- 角度单位通常是弧度，不能把度数直接传给控制器或 TF。

### 4.3 ROS 坐标约定

移动机器人常见 TF 树如下：

```text
map
└── odom
    └── base_link
        ├── base_footprint
        ├── laser
        ├── imu_link
        └── camera_link
```

核心语义：

- `map`：全局、可能跳变但长期不漂移的参考系，由定位或 SLAM 提供。
- `odom`：局部、连续、短期平滑但允许漂移的参考系，由轮速、视觉、IMU 等里程计提供。
- `base_link`：机器人主体坐标系，通常随机器人运动。
- 传感器 frame：由 URDF 或静态变换描述相对 `base_link` 的安装关系。

Nav2 的最低要求是能获得 `map -> odom -> base_link`，并能继续变换到传感器坐标系。不要同时让两个节点发布同一条动态 TF；一条 TF 只能有一个权威发布者。

### 4.4 时间是另一棵“隐形的树”

所有传感器数据都应检查：

1. `header.stamp` 是否来自正确时钟。
2. 仿真是否统一设置 `use_sim_time: true`。
3. 消息延迟是否超过 TF buffer 能够查询的范围。
4. 传感器时间戳是否同步，是否存在未来时间或回拨。
5. rosbag 回放时，算法节点和可视化工具是否都使用仿真时间。

常见故障是 TF 看起来存在，但查询指定时间的变换失败；这通常不是“TF 没发布”，而是时间戳、缓存或仿真时钟不一致。

### 4.5 向量、矩阵与雅可比：机器人数学的最小工具箱

机器人中的位置、速度、力和误差都可以表示为向量；坐标变换、运动学和传感器模型通常表示为矩阵。学习时不要只记公式，要明确矩阵两侧的物理意义。

| 数学对象 | 机器人中的含义 |
|---|---|
| 位置向量 | 点在某个坐标系中的坐标 |
| 速度向量 | 线速度、角速度或关节速度 |
| 旋转矩阵 | 一个坐标系相对另一个坐标系的方向 |
| 协方差矩阵 | 各状态量的不确定性及相关性 |
| 雅可比矩阵 | 输入微小变化到输出微小变化的局部映射 |
| 代价函数 | 规划、优化或控制中对误差的量化 |

例如移动机器人在平面上的状态可以写为：

\[
x = \begin{bmatrix}x & y & \theta\end{bmatrix}^{T}
\]

差速底盘的控制输入可以写为：

\[
u = \begin{bmatrix}v & \omega\end{bmatrix}^{T}
\]

局部线性化后，雅可比可以帮助理解速度变化对位姿变化的影响。机械臂则常用 `J(q)` 将关节速度映射为末端速度：

\[
\dot{x}=J(q)\dot{q}
\]

### 4.6 SE(2)、SE(3) 与变换逆

二维移动机器人常在 `SE(2)` 中计算，状态包含 `x`、`y` 和偏航角；机械臂、三维点云和相机标定通常需要 `SE(3)`，即三维平移和三维旋转。

齐次变换的逆不能简单地把平移向量取负。对于：

\[
T=\begin{bmatrix}R&t\\0&1\end{bmatrix}
\]

其逆为：

\[
T^{-1}=\begin{bmatrix}R^T&-R^Tt\\0&1\end{bmatrix}
\]

这说明：先把平移从目标坐标系旋回原坐标系，再取负值。常见错误是直接使用 `-t`，在两个坐标系存在旋转时会得到错误结果。

变换链应始终写清方向。例如要把激光坐标系中的点变换到地图坐标系：

\[
p_{map}=T_{map,odom}T_{odom,base}T_{base,laser}p_{laser}
\]

在 ROS 2 中，这条链通常由 TF2 根据时间戳自动查询；在离线数学代码中，则必须由程序员显式完成矩阵相乘。

### 4.7 坐标系的方向、单位与旋转顺序

坐标系问题最难排查的地方，是“看起来合理”的错误也能让系统运行。每个 frame 都应记录：

| 项目 | 应明确的内容 |
|---|---|
| 原点 | 原点位于机器人哪个物理位置 |
| 轴方向 | `x`、`y`、`z` 分别指向哪里 |
| 手性 | 是否为右手坐标系 |
| 单位 | 米、弧度、秒，还是传感器的原始单位 |
| 旋转顺序 | `roll-pitch-yaw` 的约定和应用顺序 |
| 参考对象 | 相对哪个 parent frame 定义 |

ROS 机器人通常采用右手坐标约定：前方为 `x`，左方为 `y`，上方为 `z`；但实际设备驱动可能使用自己的坐标轴，必须在驱动层或 TF 层转换，不能靠记忆猜测。

欧拉角还要注意：同一组角度在不同旋转顺序下表示不同姿态。将 CAD、URDF、相机 SDK、IMU 驱动和 ROS 2 消息中的角度直接拼接，是产生姿态错误的常见原因。工程中优先使用旋转矩阵或四元数做计算，在 UI 或日志中再转换为易读的欧拉角。

### 4.8 `map`、`odom`、`base_link` 的工程边界

这三个 frame 不是简单的“上级、下级、机器人”关系，而是不同误差特性的职责分工：

| Frame | 连续性 | 长期漂移 | 常见发布者 | 典型用途 |
|---|---|---|---|---|
| `map` | 允许跳变 | 低 | SLAM、AMCL、GPS/全局定位 | 全局目标和地图 |
| `odom` | 应连续平滑 | 允许 | 底盘、轮速/视觉/IMU 融合 | 局部控制和短期运动 |
| `base_link` | 随机器人运动 | 取决于上游 | 里程计或状态估计 | 机器人本体参考 |

推荐的数据关系：

```text
全局定位/SLAM 负责 map -> odom
局部里程计负责 odom -> base_link
URDF/静态外参负责 base_link -> sensor_link
```

如果把全局定位直接写入 `odom -> base_link`，机器人可能在定位修正时出现局部轨迹跳变；如果让两个节点同时发布同一条边，TF 树会出现竞争，结果取决于消息到达顺序。

### 4.9 TF2 的静态变换、动态变换和权威发布者

静态变换用于不会随时间变化的安装关系，例如 `base_link -> laser`；动态变换用于机器人运动关系，例如 `odom -> base_link`。选择错误会导致缓存、带宽和语义问题：

| 变换类型 | 示例 | 发布方式 |
|---|---|---|
| 静态 | `base_link -> camera_link` | URDF、`static_transform_publisher` |
| 动态 | `odom -> base_link` | 里程计、状态估计、定位节点 |
| 关节动态 | `base_link -> wheel_link` | `robot_state_publisher` + `JointState` |

TF2 调试命令：

```bash
ros2 run tf2_tools view_frames
ros2 run tf2_ros tf2_echo base_link laser
ros2 topic echo /tf --once
ros2 topic echo /tf_static --once
```

排查时要确认：

1. frame 名称是否大小写和下划线完全一致。
2. parent 和 child 是否写反。
3. 同一动态边是否只有一个发布者。
4. 变换是否带有正确时间戳。
5. 查询的时间是否早于缓存最早时间或晚于最新时间。
6. 静态变换是否被错误地作为高频动态变换发布。

### 4.10 时间模型：系统时间、ROS 时间与仿真时间

机器人中至少要区分三种时间语义：

- **墙上时钟**：操作系统当前时间，适合记录真实发生时间和运维日志。
- **ROS 时间**：节点通过 ROS 时间接口获取的时间，可映射到系统时间或仿真时间。
- **仿真时间**：由仿真器通过 `/clock` 发布，可能暂停、加速、回放或跳变。

仿真和 rosbag2 回放时，算法节点、传感器驱动、TF 发布者和可视化工具必须对 `use_sim_time` 达成一致。只给部分节点设置仿真时间，会产生“一个节点认为未来已到，另一个节点认为时间还没开始”的错误。

时间戳排查可从以下几个信号入手：

```bash
ros2 topic echo /clock --once
ros2 topic hz /clock
ros2 topic echo /scan --once
ros2 topic echo /tf --once
```

重点观察消息时间是否单调、是否明显领先当前 ROS 时间、是否长期不变化，以及不同 Topic 之间的时间差是否超过算法允许的延迟。

### 4.11 延迟、缓存和外推错误

TF 查询失败常见的错误语义包括：

- **Lookup**：请求的 frame 不存在，或 TF 树不连通。
- **Connectivity**：两个 frame 位于不同的 TF 子树。
- **Extrapolation into the past**：请求时间早于缓存范围。
- **Extrapolation into the future**：请求时间晚于最新 TF 数据。

不要用盲目增大 `transform_tolerance` 代替解决延迟问题。应先测量：

\[
\text{端到端延迟}=t_{control}-t_{sensor}
\]

并分别拆分驱动、网络、队列、计算、TF 发布和控制执行的耗时。队列太深会让数据“仍然存在”但已经过时；队列太浅则可能丢失消息。机器人控制通常更关心新鲜数据，而不是尽可能保留所有历史数据。

### 4.12 协方差与误差传播

位姿不是一个绝对正确的数，而是带有不确定性。二维位姿常用协方差矩阵表示：

\[
\Sigma=\begin{bmatrix}
\sigma_x^2 & \sigma_{xy} & \sigma_{x\theta}\\
\sigma_{xy} & \sigma_y^2 & \sigma_{y\theta}\\
\sigma_{x\theta} & \sigma_{y\theta} & \sigma_\theta^2
\end{bmatrix}
\]

对传感器融合而言，协方差决定系统对观测的信任程度。把“未知”随意填成零，可能被下游理解为“完全准确”；把协方差设得过小，则会让错误传感器强行拉动估计。实际配置应根据传感器测量噪声、标定结果、运动状态和异常情况确定。

坐标变换也会传播误差：外参不准、轮径不准或时间不同步都会使下游地图、定位和规划出现系统性误差。遇到持续偏移时，应区分随机噪声和系统误差：前者需要滤波，后者需要标定或修正模型。

### 4.13 一个二维坐标变换练习

设机器人在地图坐标系中的位姿为 `(2.0 m, 1.0 m, 90°)`，激光点在机器人坐标系中为 `(1.0 m, 0.0 m)`。由于机器人朝向地图 `y` 轴正方向，该点在地图坐标系中的位置应接近 `(2.0 m, 2.0 m)`。

手算时按以下顺序：

1. 把角度从度转换为弧度。
2. 构造二维旋转矩阵。
3. 先旋转机器人坐标系中的点。
4. 再加上机器人在地图中的平移。
5. 用 RViz2 或 Python 数值计算验证结果。

对应的二维公式为：

\[
\begin{bmatrix}x_A\\y_A\end{bmatrix}
=
\begin{bmatrix}x_0\\y_0\end{bmatrix}
+
\begin{bmatrix}
\cos\theta&-\sin\theta\\
\sin\theta&\cos\theta
\end{bmatrix}
\begin{bmatrix}x_B\\y_B\end{bmatrix}
\]

通过这个简单例子，可以验证旋转方向、角度单位、矩阵顺序和坐标系语义，避免直接从复杂 SLAM 或 Nav2 问题开始排查。

- 说明 `SE(2)` 与 `SE(3)` 的适用场景。
- 解释 `map`、`odom`、`base_link` 和传感器 frame 的职责边界。
- 区分静态 TF、动态 TF 和关节 TF，并找到每条边的权威发布者。
- 解释系统时间、ROS 时间、仿真时间、消息时间戳和 TF 缓存的关系。
- 根据 Lookup、Connectivity 和 Extrapolation 错误判断排查方向。

## 5. 机器人建模：URDF、Xacro、SDF

### 5.1 URDF 的结构

URDF 用 `link` 描述刚体，用 `joint` 描述刚体之间的连接：

```xml
<link name="base_link">
  <visual>
    <geometry><box size="0.4 0.3 0.12"/></geometry>
  </visual>
  <collision>
    <geometry><box size="0.4 0.3 0.12"/></geometry>
  </collision>
  <inertial>
    <origin xyz="0 0 0"/>
    <mass value="8.0"/>
    <inertia ixx="0.12" ixy="0" ixz="0"
             iyy="0.18" iyz="0" izz="0.24"/>
  </inertial>
</link>

<joint name="laser_joint" type="fixed">
  <parent link="base_link"/>
  <child link="laser"/>
  <origin xyz="0.18 0 0.16" rpy="0 0 0"/>
</joint>
```

三种几何体必须分开思考：

- `visual`：为了看起来像真实机器人，可以使用复杂网格。
- `collision`：为了碰撞检测，优先使用简单、稳定、不过度重叠的几何体。
- `inertial`：为了动力学仿真，必须与真实质量、质心和惯量相符。

只写 `visual` 不等于机器人拥有可用碰撞模型；只写一个随意的惯量也不等于仿真会稳定。

### 5.2 Joint 类型和常见错误

| Joint | 用途 |
|---|---|
| `fixed` | 传感器、外壳、支架等固定连接 |
| `revolute` | 有上下限的旋转关节 |
| `continuous` | 可无限旋转的轮子或转盘 |
| `prismatic` | 直线滑动关节 |
| `floating` | 需要谨慎使用的自由连接 |
| `planar` | 平面运动，实际工程中使用较少 |

常见错误包括：父子 link 写反、旋转轴方向错误、轮子半径与实际不符、关节原点偏移错误、惯性矩阵不满足物理正定性、碰撞网格尺度错误、单位混用毫米和米。

### 5.3 Xacro：把模型变成可维护代码

当机器人出现左右对称轮子、多个传感器、不同底盘尺寸时，应使用 Xacro 宏和属性：

```xml
<xacro:property name="wheel_radius" value="0.06"/>
<xacro:property name="wheel_width" value="0.03"/>

<xacro:macro name="wheel" params="name x y">
  <link name="${name}_link">...</link>
  <joint name="${name}_joint" type="continuous">
    <parent link="base_link"/>
    <child link="${name}_link"/>
    <origin xyz="${x} ${y} 0"/>
    <axis xyz="0 1 0"/>
  </joint>
</xacro:macro>
```

模型文件建议分为 `materials.xacro`、`inertials.xacro`、`wheels.xacro`、`sensors.xacro` 和主入口文件。用参数控制仿真插件、传感器开关和命名空间，避免复制出多个相互漂移的 URDF。

### 5.4 SDF 与 Gazebo

URDF 主要描述机器人树和 ROS 生态中的机器人模型；SDF 更适合描述完整仿真世界、模型、传感器、插件、灯光和物理参数。工程上经常采用：

```text
Xacro/URDF：机器人描述、TF、visual/collision/inertial
SDF：仿真世界、物理引擎、模型插件、环境
ros_gz_bridge：Gazebo Transport 与 ROS 2 Topic/Service 的桥接
```

不要把“Gazebo 能显示模型”和“机器人动力学正确”混为一谈。必须分别验证 TF、碰撞、惯性、关节运动、传感器数据和控制闭环。

### 5.5 一个机器人模型的五个层次

同一个机器人通常需要同时服务于可视化、碰撞检测、动力学仿真、运动规划和控制。不要把“模型”理解成一个只有外形的三维文件。

| 层次 | 描述内容 | 主要消费者 | 典型要求 |
|---|---|---|---|
| 结构层 | link、joint、parent、child 和关节轴 | TF、运动学、`robot_state_publisher` | 树结构正确、无环、frame 清晰 |
| 外观层 | visual 几何、材质和颜色 | RViz2、Gazebo 显示 | 尺寸、原点和材质正确 |
| 碰撞层 | collision 几何和接触边界 | Nav2、MoveIt 2、物理引擎 | 简化、封闭、不过度重叠 |
| 动力学层 | 质量、质心、惯性、摩擦和阻尼 | Gazebo、控制器、动力学算法 | 参数具有物理意义且稳定 |
| 接口层 | 关节限制、控制接口、传感器和插件 | `ros2_control`、驱动、仿真 | 接口名称和单位与硬件一致 |

一个模型可以在 RViz2 中外观正确，却在 Gazebo 中翻倒；也可以在 Gazebo 中运动，却因为碰撞模型过小而让 Nav2 穿过障碍。验收时必须按层次分别确认。

### 5.6 `link`、`joint` 与坐标原点

每个 `link` 都有自己的坐标系，`joint` 的 `<origin>` 描述 child link 坐标系相对于 parent link 坐标系的位置和姿态。`visual`、`collision` 和 `inertial` 又可以通过各自的 `<origin>` 相对 link 坐标系偏移。

建议画出这样的关系：

```text
parent link frame
        │
        └── joint origin + joint axis
                    │
                    └── child link frame
                              ├── visual origin
                              ├── collision origin
                              └── inertial origin
```

常见错误不是 XML 语法错误，而是“坐标都合法但语义不对”：

- 把 `joint` 的原点误当成 child link 的几何中心。
- 只移动 visual 网格，没有同步 collision 和 inertial。
- 轮子的旋转轴方向与实际轮轴不一致。
- 使用 `rpy` 时忘记旋转顺序和弧度单位。
- 父子关系反了，导致 TF 方向与运动学预期相反。

建模时建议先用简单盒体、圆柱体验证坐标和运动，再替换复杂 mesh。复杂网格不应该成为排查坐标问题的第一变量。

### 5.7 `visual`、`collision` 和 mesh 资源

#### Visual 模型

Visual 模型优先服务于可读性和显示效果，可以使用高精度网格、材质和纹理，但要确认单位和坐标原点。CAD 导出的模型经常使用毫米，而 ROS 2/URDF 通常按米解释；缩放错误会让机器人看起来大一千倍或小一千倍。

#### Collision 模型

Collision 模型优先服务于速度和安全边界：

- 移动底盘可使用盒体、圆柱体或少量凸包近似。
- 机械臂应覆盖连杆外廓和工具真实危险区域。
- 不要让相邻 link 的 collision 在静止姿态下大面积互相穿插。
- 不要为了“看起来精确”直接使用数十万三角形的复杂网格。
- 碰撞模型过小会造成穿模，过大则会导致规划过于保守。

#### 资源路径

使用 mesh 时应统一资源组织和 URI：

```xml
<mesh filename="package://robot_description/meshes/base.dae"
      scale="1 1 1"/>
```

验证资源时要确认：包名正确、文件被安装、路径大小写一致、mesh 在目标机器上存在、缩放和坐标系符合预期。Windows 或大小写不敏感的开发环境中能打开，不代表 Linux 真机上一定能找到。

### 5.8 惯性、质量与质心

动力学仿真至少需要质量、惯性原点和惯性矩阵。惯性矩阵通常写成：

\[
I=\begin{bmatrix}
I_{xx}&I_{xy}&I_{xz}\\
I_{xy}&I_{yy}&I_{yz}\\
I_{xz}&I_{yz}&I_{zz}
\end{bmatrix}
\]

工程上应注意：

1. 质量单位使用千克，长度使用米。
2. 惯性原点尽量放在真实质心位置。
3. 惯性矩阵应对称，并满足物理上合理的正定性。
4. 薄板、长杆和圆柱的惯量不能用随意的对角值代替。
5. 复杂总成可以由 CAD、实验测量或多个部件组合得到。
6. 质量、质心和 collision/visual 的相对位置应互相一致。

若机器人一启动就剧烈抖动、翻倒、弹飞或关节速度异常，优先检查惯性和碰撞接触，而不是先调大控制器增益。惯性过小、质心偏离、碰撞重叠或摩擦参数不合理都可能使仿真不稳定。

### 5.9 Joint 限制、动态参数与控制接口

关节模型不仅需要 `type` 和 `axis`，还应根据关节用途声明限制：

```xml
<limit lower="-1.57"
       upper="1.57"
       effort="10.0"
       velocity="2.0"/>
<dynamics damping="0.1" friction="0.02"/>
```

| 参数 | 含义 | 风险 |
|---|---|---|
| `lower`/`upper` | 位置上下限 | 缺失或错误会导致规划越界 |
| `effort` | 允许的力或力矩 | 过大可能掩盖硬件能力限制 |
| `velocity` | 最大关节速度 | 影响轨迹时间和安全 |
| `damping` | 阻尼 | 太小容易振荡，太大运动迟钝 |
| `friction` | 摩擦近似 | 影响启动、停止和稳态误差 |

URDF 中的限制是模型层约束，不等于硬件驱动一定会执行。真实系统还需要在控制器、驱动器和安全层重复检查限速、限位和故障状态。仿真和真机应使用一致的关节名称、单位、正方向和接口语义。

### 5.10 URDF、Xacro、SDF、SRDF 和 `ros2_control` 的边界

| 文件/系统 | 主要职责 | 不应承担的职责 |
|---|---|---|
| URDF | 机器人 link/joint 结构、外观、碰撞、惯性 | 完整仿真世界和任务规划语义 |
| Xacro | 参数化、宏、条件和文件复用 | 运行时状态管理 |
| SDF | 仿真世界、模型插件、传感器和物理配置 | 替代所有 ROS 2 接口设计 |
| SRDF | MoveIt 规划组、虚拟关节、自碰撞禁用 | 替代 URDF 的几何和惯性 |
| `ros2_control` | 硬件接口、命令接口、状态接口和控制器 | 自动修正错误模型或标定 |

推荐的工程链路：

```text
Xacro 参数和宏
        ↓ 展开
URDF 机器人描述
        ├── robot_state_publisher → TF
        ├── RViz2 → 外观和关节显示
        ├── MoveIt 2/SRDF → 运动规划
        ├── Gazebo/SDF → 物理仿真
        └── ros2_control → 仿真或真机控制接口
```

这样可以把机器人几何、规划语义、仿真插件和硬件驱动分层维护，减少“一份 XML 包含所有逻辑”带来的耦合。

### 5.11 传感器建模与 frame 约定

传感器模型至少包含安装位置、安装姿态、数据 Topic 和消息中的 `frame_id`：

```text
base_link
├── laser_link
├── imu_link
├── camera_link
└── camera_optical_frame
```

不要把 `camera_link` 和 `camera_optical_frame` 混为一谈。相机驱动可能需要符合光学坐标约定的 optical frame；激光、IMU 和底盘也可能有各自的轴方向。传感器在 RViz2 中显示正确，需要同时满足：

- URDF/静态 TF 的安装外参正确。
- 驱动发布的 `frame_id` 与 TF 名称完全一致。
- 消息时间戳可以查询到对应时刻的 TF。
- 仿真和真机的传感器朝向、视场、分辨率和噪声有明确差异记录。

### 5.12 模型验证工作流

不要等到 Gazebo 或 Nav2 启动失败才检查 URDF。建议按以下顺序验证：

```bash
# 展开 Xacro
xacro robot.urdf.xacro > /tmp/robot.urdf

# 检查 XML 和 URDF 结构
check_urdf /tmp/robot.urdf

# 查看机器人描述和 TF
ros2 run robot_state_publisher robot_state_publisher /tmp/robot.urdf
ros2 run tf2_tools view_frames

# 在 RViz2 中检查外观、关节和传感器
ros2 run rviz2 rviz2
```

验证顺序：

1. XML/Xacro 能否展开。
2. link/joint 是否形成单根树，没有孤立 link 或环。
3. joint 类型、轴、原点和限制是否正确。
4. visual、collision、inertial 是否在同一尺度和位置。
5. `robot_state_publisher` 是否发布预期 TF。
6. RViz2 中模型、轮子和传感器是否符合实物。
7. 再接入 Gazebo、传感器插件和 `ros2_control`。

### 5.13 常见建模错误与现象

| 现象 | 可能原因 | 优先检查 |
|---|---|---|
| 模型整体大小错误 | mesh 单位或 `scale` 错误 | CAD 单位、mesh scale |
| 轮子方向异常 | joint axis 或 rpy 错误 | 轮轴方向、左右轮符号 |
| RViz2 显示但 Gazebo 翻倒 | 惯性、质心或碰撞错误 | mass、inertial、collision |
| 机器人穿过障碍 | collision 缺失或过小 | collision 几何和尺寸 |
| MoveIt 规划碰撞过多 | collision 过大或自碰撞配置错误 | 简化模型、SRDF 矩阵 |
| 传感器数据错位 | 外参或 frame 错误 | TF、`frame_id`、时间戳 |
| 关节无法运动 | 类型、axis、limit 或控制接口错误 | joint 配置、controller |
| mesh 在本机能加载、真机失败 | 资源未安装或路径大小写错误 | `package://` 路径和安装规则 |

### 5.14 第五章学习验收

完成本章后，至少应能够：

- 解释 `link`、`joint`、`visual`、`collision` 和 `inertial` 的边界。
- 使用 Xacro 宏和参数生成左右对称的轮子或传感器模型。
- 说明 joint origin、link frame、visual origin 和 inertial origin 的区别。
- 根据实际尺寸和质量建立一个基础动力学模型。
- 为关节配置方向、限位、速度、力矩、阻尼和摩擦。
- 区分 URDF、Xacro、SDF、SRDF 和 `ros2_control` 的职责。
- 使用 `xacro`、`check_urdf`、`robot_state_publisher` 和 RViz2 完成逐层验证。
- 解释 mesh 单位、碰撞简化、惯性错误和传感器外参错误的典型现象。

第五章的交付物应包括：一份可展开的 Xacro 模型、一个含 visual/collision/inertial 的基础 link、至少一个可运动 joint、一张 TF 树、一份模型检查记录，以及一份仿真与真机模型差异清单。

## 6. 移动机器人运动学与控制

### 6.1 差速底盘

设左右轮线速度为 `v_l`、`v_r`，轮距为 `b`，则车体中心速度为：

\[
v=\frac{v_r+v_l}{2},\qquad
\omega=\frac{v_r-v_l}{b}
\]

反解为：

\[
v_l=v-\frac{b\omega}{2},\qquad
v_r=v+\frac{b\omega}{2}
\]

差速机器人不能直接横移，控制输入通常是 `cmd_vel.linear.x` 和 `cmd_vel.angular.z`。若左右轮半径、轮距或轮子轴方向写错，直行会偏、旋转角度不准或里程计持续漂移。

### 6.2 全向和 Ackermann 底盘

全向底盘可在平面内控制 `v_x`、`v_y`、`ω`，但需要根据轮子布局建立逆运动学矩阵，并严格校准每个轮子的半径、安装角和零位。Ackermann 底盘有转向角和最小转弯半径，不能使用差速模型直接替代。

选择导航控制器前先确认底盘模型：

| 底盘 | 关键约束 | 常见控制关注点 |
|---|---|---|
| 差速 | `v_y = 0` | 轮距、轮径、角速度、原地旋转 |
| 全向 | 可横移 | 轮速分配、侧滑、各向限速 |
| Ackermann | 转向角和曲率 | 最小半径、前轮角度、倒车 |

### 6.3 从 `/cmd_vel` 到电机

控制链路应明确为：

```text
规划器/控制器
  → geometry_msgs/msg/Twist
  → 底盘运动学逆解
  → 轮速或转向角目标
  → PID/前馈/电机驱动
  → 编码器反馈
  → odom 和诊断
```

如果 `/cmd_vel` 在变化但机器人不动，不能立即调 Nav2。先验证底盘驱动是否订阅、速度是否被限幅、控制器是否 active、电机是否使能、编码器是否变化，以及急停和看门狗是否生效。

### 6.4 PID 的工程理解

PID 可写为：

\[
u(t)=K_p e(t)+K_i\int e(t)dt+K_d\frac{de(t)}{dt}
\]

- `K_p` 增大通常使响应更快，但过大可能振荡。
- `K_i` 用于消除稳态误差，但必须防止积分饱和。
- `K_d` 可抑制变化过快，但对噪声敏感，常配合滤波。

实际电机控制还要考虑死区、摩擦、饱和、采样周期、通信延迟、编码器分辨率和电池电压变化。PID 不是用来弥补错误坐标系或错误轮径的。

### 6.5 非完整约束与底盘可行性

移动机器人不能任意改变位姿速度。差速机器人在理想平面运动中满足：

\[
\dot{x}=v\cos\theta,\qquad
\dot{y}=v\sin\theta,\qquad
\dot{\theta}=\omega
\]

它的侧向速度受到约束：

\[
v_y=0
\]

这就是非完整约束的直观表现：机器人可以向前后运动，也可以改变朝向，但不能像全向底盘一样直接横移。全局规划器和局部控制器必须知道底盘模型，否则会生成几何上存在、物理上无法跟踪的路径。

底盘控制前应明确：

| 项目 | 差速底盘 | 全向底盘 | Ackermann 底盘 |
|---|---|---|---|
| 可直接控制 | `v_x`、`ω` | `v_x`、`v_y`、`ω` | 纵向速度、转向角 |
| 横向速度 | 不可直接产生 | 可以产生 | 不可直接产生 |
| 原地旋转 | 可以 | 通常可以 | 通常不可以 |
| 关键模型参数 | 轮径、轮距 | 轮径、轮距、滚轮角 | 轴距、转向几何、最小半径 |
| 常见误用 | 把横移命令当成可执行 | 忽略侧滑和轮速上限 | 使用差速模型控制 |

### 6.6 从轮速积分位姿和里程计

编码器通常先得到轮子的角速度，再根据轮半径换算为线速度：

\[
v_l=r\omega_l,\qquad v_r=r\omega_r
\]

差速底盘在一个采样周期 `\Delta t` 内可以用以下方法更新位姿：

```text
读取左右轮编码器
    ↓
计算轮速或轮位移
    ↓
计算车体线速度 v 和角速度 ω
    ↓
根据当前 θ 积分 x、y、θ
    ↓
发布 nav_msgs/msg/Odometry
    ↓
发布 odom -> base_link
```

简单欧拉积分为：

\[
x_{k+1}=x_k+v_k\cos\theta_k\Delta t
\]

\[
y_{k+1}=y_k+v_k\sin\theta_k\Delta t
\]

\[
\theta_{k+1}=\theta_k+\omega_k\Delta t
\]

当角速度较大或采样周期较长时，应使用精确的圆弧积分或中点积分，避免把曲线运动近似成过大的直线误差。发布里程计时还要同步填写：

- `header.stamp`。
- `header.frame_id`，通常是 `odom`。
- `child_frame_id`，通常是 `base_link`。
- pose 和 twist 的单位。
- pose/twist covariance。
- TF 发布开关，避免与其他节点重复发布。

### 6.7 里程计误差与底盘标定

轮式里程计的主要误差来源包括：

- 左右轮半径不一致。
- 轮距估计错误。
- 轮胎磨损、地面摩擦和侧滑。
- 编码器分辨率或方向配置错误。
- 采样周期和时间戳不准确。
- 轮子接触点不在理想几何位置。
- 机械结构松动、背隙和悬挂变形。

典型现象：

| 现象 | 可能原因 |
|---|---|
| 直行轨迹弯向一侧 | 左右轮径或速度比例不一致 |
| 原地旋转角度偏大/偏小 | 轮距参数错误 |
| 前进距离总是偏长/偏短 | 轮径、编码器比例或单位错误 |
| 地图中出现周期性重影 | 轮滑、时间同步或外参问题 |
| 左右方向符号相反 | 编码器或 joint axis 方向错误 |

基础标定流程：

1. 让机器人低速直行固定距离，比较实际距离与 odom 距离，修正轮径或编码器比例。
2. 让机器人原地旋转固定角度，比较实际角度与 odom 角度，修正轮距。
3. 重复正向和反向实验，区分比例误差、死区和机械回差。
4. 在不同地面和不同速度下验证，避免只对单一场景过拟合。
5. 保存标定参数、实验距离、地面条件和剩余误差。

### 6.8 控制闭环的层次

移动机器人通常不是一个 PID，而是多层闭环：

```text
任务/导航层：目标点、全局路径、局部轨迹
        ↓
底盘速度层：期望 v、ω 或转向角
        ↓
轮速/关节层：期望轮速与实际轮速闭环
        ↓
电机电流/驱动层：电机执行与保护
        ↓
编码器、IMU、电流和温度反馈
```

每一层的误差和频率不同：

| 层次 | 主要误差 | 常见频率关注 |
|---|---|---|
| 任务/规划 | 目标距离、路径偏差 | 低频，关注任务进展 |
| 速度控制 | 期望速度与实际速度 | 中高频，关注跟踪和限速 |
| 轮速控制 | 单轮速度误差 | 高频，关注响应、死区和饱和 |
| 电机驱动 | 电流、转矩和保护 | 由驱动器或 MCU 实时执行 |

上层控制器不应直接补偿下层机械错误。比如 Nav2 中的路径偏差，可能根本原因是轮速 PID 没调好或 odom 方向错误；必须先修复底层闭环，再评价上层控制算法。

### 6.9 PID、前馈与抗积分饱和

离散 PID 实现时，积分和微分项必须考虑采样周期：

\[
u_k=K_pe_k+K_i\sum_{i=0}^{k}e_i\Delta t
+K_d\frac{e_k-e_{k-1}}{\Delta t}
\]

工程实现需要增加以下保护：

- **输出限幅**：速度、加速度、电流和力矩不能超过硬件限制。
- **积分限幅**：防止输出饱和时积分继续累积。
- **积分分离**：误差很大或执行器饱和时暂时停止积分。
- **微分滤波**：避免编码器噪声直接放大到控制输出。
- **设定值加速度限制**：避免目标突变造成冲击。
- **异常复位**：急停、控制器失活或切换模式时清理积分状态。

单纯 PID 在不同速度、电池电压和负载下可能表现不同，可以加入前馈项：

```text
控制输出 = 速度前馈 + PID 误差修正 + 摩擦补偿
```

前馈负责“预计需要多少输出”，反馈负责“修正实际误差”。前馈不能替代反馈，也不能用来掩盖编码器方向或速度单位错误。

### 6.10 死区、饱和、加速度和 jerk

真实底盘往往存在最小启动电压或速度死区：命令很小但电机不动，命令超过阈值后突然启动。这会导致机器人在目标附近抖动或无法保持极低速。

控制器应明确处理：

| 约束 | 作用 |
|---|---|
| 速度上限 | 防止运动过快 |
| 加速度上限 | 防止启动和停止冲击 |
| jerk 限制 | 限制加速度变化，改善平顺性 |
| 电流/力矩上限 | 保护电机、驱动器和机械结构 |
| 死区补偿 | 克服低速不动作，但不能造成突然跳变 |
| 超时归零 | 控制命令失联后进入安全状态 |

限幅最好在多个安全边界重复执行：上层导航限制、底盘控制器限制、驱动器硬件限制。这样某一层参数错误时，仍有其他保护层兜底。

### 6.11 `ros2_control` 与底盘接口

一个典型底盘控制接口包括：

```text
读取：轮子位置、轮子速度、关节状态、故障码
写入：轮子速度、轮子位置或电机力矩
        ↓
controller_manager
        ↓
diff_drive_controller / 自定义控制器
        ↓
cmd_vel、odom、joint_states
```

检查控制链路时，不要只看 `/cmd_vel`：

```bash
ros2 control list_controllers
ros2 control list_hardware_interfaces
ros2 topic echo /joint_states --once
ros2 topic echo /odom --once
ros2 topic info /cmd_vel --verbose
```

需要确认：

- 控制器是否处于 `active`。
- 命令接口和状态接口名称是否与 URDF、硬件插件和控制器配置一致。
- 左右轮 joint 名称、方向和半径是否匹配。
- 控制器是否发布 odom，是否由其他节点重复发布 TF。
- 硬件 read/write 周期是否稳定。
- 失去命令或硬件故障时是否自动停止。

### 6.12 速度命令的安全门

`/cmd_vel` 不应被视为“任何节点都能直接控制电机”的无限权限接口。工程上可以增加一个速度安全门：

```text
上层 cmd_vel
    ↓
命令仲裁器
    ├── 急停状态检查
    ├── 传感器健康检查
    ├── 速度/加速度限幅
    ├── 控制命令超时检查
    └── 优先级和来源校验
    ↓
底盘控制器
```

多个来源同时发布速度时，应明确优先级，例如人工遥控、导航、自动对接和安全停止。停止命令必须能够覆盖普通运动命令，且网络中断、节点崩溃、消息超时和急停都应有确定行为。

### 6.13 运动控制调试顺序

建议使用“静态检查 → 单轮 → 双轮 → 里程计 → 速度闭环 → 上层导航”的顺序：

1. 静态检查 joint 名称、轴方向、轮半径、轮距和单位。
2. 抬起底盘，低速测试单个轮子的正负方向。
3. 低速同时驱动左右轮，确认直行和原地旋转方向。
4. 观察编码器、`/joint_states` 和 `/odom` 是否同步变化。
5. 记录期望速度与实际速度，调节轮速 PID 和前馈。
6. 测量直行、旋转、停止和反向误差，完成底盘标定。
7. 最后接入局部控制器、代价地图和 Nav2。

不要在底盘尚未完成基础闭环时直接运行高速导航。真机首次测试应使用低速、空旷场地、远程急停和人工接管。

### 6.14 第六章学习验收

完成本章后，至少应能够：

- 推导差速底盘的正运动学和逆运动学。
- 解释差速、全向和 Ackermann 底盘的运动约束。
- 根据编码器计算轮速、车体速度和 odom 位姿。
- 通过直行和旋转实验标定轮径、轮距和编码器比例。
- 区分任务层、速度层、轮速层和电机驱动层控制闭环。
- 实现带限幅、积分保护、微分滤波和超时停止的 PID 控制。
- 使用 `ros2_control` CLI 检查控制器、硬件接口、关节状态和 odom。
- 说明 `/cmd_vel` 多来源仲裁、看门狗和急停的必要性。
- 用曲线或 rosbag 比较期望速度、实际速度、位姿误差和停止距离。

第六章的交付物应包括：一个底盘运动学说明、一个轮速到 odom 的计算记录、一次轮径/轮距标定报告、一组速度闭环曲线，以及一份包含限速、超时和急停行为的安全测试记录。

## 7. 传感器、标定与数据质量

### 7.1 常见传感器

| 传感器 | 主要用途 | 关键字段/风险 |
|---|---|---|
| 编码器 | 轮速和关节位置 | 分辨率、方向、轮径、滑移 |
| IMU | 角速度、加速度、姿态辅助 | bias、坐标轴、重力处理、磁干扰 |
| 2D LiDAR | 平面障碍、建图、定位 | 扫描平面、遮挡、反光、时间戳 |
| 3D LiDAR | 点云、三维感知 | 外参、点云密度、畸变、带宽 |
| RGB/深度相机 | 视觉、深度、目标检测 | 内参、外参、曝光、深度空洞 |
| 力/力矩传感器 | 接触和柔顺控制 | 零偏、坐标系、采样同步 |
| GPS/RTK | 室外全球定位 | 漂移、遮挡、坐标投影、失锁 |

### 7.2 标定分为三类

1. **内参标定**：相机焦距、主点、畸变，LiDAR 的距离和角度误差等。
2. **外参标定**：传感器相对 `base_link` 的平移和旋转。
3. **系统标定**：轮径、轮距、编码器比例、IMU bias、时间偏移和控制死区。

外参错误通常表现为点云和机器人模型错位、激光地图重影、相机深度与彩色图错位；轮径或轮距错误则表现为直行偏移、原地旋转角误差和闭环漂移。

### 7.3 传感器数据验收

对每个传感器至少检查：

- Topic 类型、频率和 QoS。
- `frame_id` 是否正确且能在 TF 树中查询。
- 时间戳是否单调、是否与仿真时钟一致。
- 单位是否正确，例如米、弧度、米每秒。
- 数据是否有 NaN、Inf、越界值或长时间不变化。
- 断电、遮挡、网络抖动和驱动重启后是否能恢复。

### 7.4 传感器不是“真值源”

每个传感器都只在特定条件下可靠。选择传感器时，不要只看分辨率、量程或宣传精度，还要考虑环境、安装位置、输出频率、延迟、带宽、维护成本和失效模式。

| 传感器 | 擅长提供 | 不擅长或容易失效 |
|---|---|---|
| 编码器 | 高频相对运动 | 打滑、轮径误差、机械回差 |
| IMU | 高频角速度和加速度变化 | 长期 bias、振动、磁干扰和安装轴误差 |
| 2D LiDAR | 平面障碍和几何结构 | 玻璃、低矮/高处障碍、动态遮挡 |
| 3D LiDAR | 空间点云和三维结构 | 带宽、雨雾、反射材质、运动畸变 |
| RGB 相机 | 颜色、纹理和目标外观 | 光照变化、遮挡、尺度和深度缺失 |
| 深度相机 | 近距离深度和物体轮廓 | 远距离、强光、透明/反光表面 |
| GPS/RTK | 室外全局位置 | 室内、遮挡、多路径和失锁 |
| 力/力矩传感器 | 接触力和交互状态 | 零偏、结构振动、坐标和温漂 |

因此，传感器融合不是简单地“把数据相加”，而是根据每个传感器的误差特性，在合适的时间、坐标系和状态下使用它。

### 7.5 采样率、延迟和带宽

数据质量至少有四个维度：

1. **新鲜度**：消息从采集到被使用经过了多久。
2. **稳定性**：发布频率是否稳定，是否存在丢帧和突发堆积。
3. **精度**：测量值与真实值的偏差大小。
4. **完整性**：是否存在 NaN、Inf、越界、空帧或错误 frame。

可以把端到端延迟拆分为：

```text
传感器采集
  → 驱动读取
  → 数据序列化/传输
  → ROS 2 队列
  → 算法处理
  → TF 查询和变换
  → 控制或规划使用
```

检查频率和带宽：

```bash
ros2 topic hz /scan
ros2 topic bw /camera/image_raw
ros2 topic info /points --verbose
```

不要只看平均频率。机器人控制更关心最大间隔、抖动和最旧消息年龄。一个标称 `30 Hz` 的相机，如果偶尔出现数百毫秒停顿，视觉控制仍可能不稳定。

### 7.6 编码器与 IMU

#### 编码器

编码器数据应验证：

- 计数方向与机器人正方向一致。
- 位置是否连续，重启后零位语义是否明确。
- 速度是否由硬件计算，还是由位置差分得到。
- 分辨率、减速比、轮径和采样周期是否匹配。
- 轮子悬空和落地时数据是否符合预期。

编码器速度由差分得到时，采样抖动和量化误差会被放大。必要时使用时间戳差分、低通滤波和合理的异常值检测，但不要用过强滤波掩盖真实的急停或打滑。

#### IMU

IMU 通常提供角速度、线加速度和可能的姿态估计。使用前应明确：

- 加速度是否包含重力。
- 姿态是由 IMU 内部融合得到，还是由 ROS 2 节点计算。
- 坐标轴和角速度正方向是否符合 ROS 约定。
- 单位是否是 `rad/s`、`m/s²`，而不是度每秒或 `g`。
- 是否存在磁力计干扰、温漂和强振动。

静止测试可以检查零偏和噪声：让机器人保持静止，记录一段 IMU 数据，计算均值、方差和轴间相关性。移动后再观察 bias 是否变化，不能只用静止时的一个数值作为永久配置。

### 7.7 LiDAR、点云与障碍数据

2D LiDAR 重点检查扫描平面、角度范围、量程、无效值和遮挡。3D LiDAR 还要检查点云坐标、点字段、时间信息、点云畸变和下游滤波。

对于 `LaserScan`，至少确认：

```text
angle_min / angle_max
angle_increment
range_min / range_max
scan_time / time_increment
ranges 中的 NaN、Inf 和无效量程
header.frame_id 和时间戳
```

对于 `PointCloud2`，至少确认：

- `frame_id` 是传感器坐标系还是已经变换后的坐标系。
- `x/y/z` 字段是否存在且单位为米。
- 是否包含强度、环号、时间偏移等字段。
- 点云是否需要体素降采样、裁剪和地面分割。
- 传感器旋转或机器人运动期间是否存在点云畸变。

在 RViz2 中看到点云，不代表点云已经可以用于导航。还要验证点云到 costmap 的转换、障碍高度、清除射线、传感器可见范围和动态障碍处理。

### 7.8 相机内参、畸变与深度

针孔相机模型可以写为：

\[
u=f_x\frac{X}{Z}+c_x,\qquad
v=f_y\frac{Y}{Z}+c_y
\]

其中 `f_x`、`f_y` 是焦距，`c_x`、`c_y` 是主点，`Z` 是点到相机光心的深度。镜头畸变会使理想投影偏离真实像素，需要使用内参和畸变系数进行校正。

相机数据链路通常包括：

```text
相机采集
  → camera_info 内参
  → 图像去畸变/同步
  → 深度或特征提取
  → camera optical frame
  → TF 变换到 base_link/map
  → 检测、定位或点云融合
```

检查相机时不要只看图像是否显示，还要检查 `camera_info` 是否与当前分辨率、裁剪和 binning 配套。分辨率改变后沿用旧内参，是视觉定位和点云投影错误的常见原因。

### 7.9 三类标定的实际流程

#### 内参标定

得到相机焦距、主点、畸变，或传感器自身的距离、角度和偏置参数。标定数据应覆盖不同位置和姿态，不能让所有样本都集中在图像中心或同一深度。

#### 外参标定

求传感器与机器人主体或传感器之间的刚体变换：

```text
base_link
  ↔ lidar_link
  ↔ camera_link
  ↔ imu_link
```

标定后必须在独立场景验证，而不是只看标定程序的优化残差。对 LiDAR/相机外参，可检查墙面、棋盘格、平面或已知物体是否在不同位置重合。

#### 系统标定

包括轮径、轮距、编码器比例、IMU bias、时间偏移、相机曝光、控制死区和传感器安装刚度。这类参数常常与运动速度、负载、温度和地面有关，需要记录测试条件。

### 7.10 时间同步与数据对齐

多传感器融合前，至少有三种时间需要区分：

- 设备内部采集时间。
- 驱动收到并发布消息的时间。
- 算法真正消费消息的时间。

如果相机、LiDAR 和 IMU 的时间基准不同，即使外参完全正确，机器人运动时也会出现空间错位。时间对齐方法包括硬件触发、共同时钟、网络时间同步、驱动时间偏移补偿和软件近似同步。

软件同步时要注意：

- 精确同步可能丢弃没有配对的数据。
- 近似同步可以容忍时间差，但要记录允许窗口。
- 时间窗口过大，会把机器人不同姿态的数据错误配对。
- 只比较消息到达时间，不能替代比较消息采集时间。

### 7.11 噪声、异常值与数据质量指标

传感器质量评估建议建立可量化指标：

| 指标 | 含义 | 示例 |
|---|---|---|
| 频率 | 单位时间消息数量 | 实际频率与目标频率的偏差 |
| 最大间隔 | 两帧之间最长空窗 | 检测通信抖动和丢帧 |
| 延迟 | 采集到消费的时间 | 控制和融合的实时性 |
| 有效比例 | 可用数据占比 | 点云有效点、图像成功帧 |
| 越界率 | 不符合范围的数据比例 | 距离、速度、温度异常 |
| 静止噪声 | 不运动时的均值和方差 | IMU、编码器、力传感器 |
| 重复性 | 相同场景下结果一致程度 | 标定和检测稳定性 |

异常处理可以采用：

1. 范围检查：拒绝不可能的值。
2. 时间检查：拒绝过旧、未来或回拨数据。
3. 连续性检查：检测突跳、长时间不变和计数器回绕。
4. 交叉检查：与其他传感器或运动模型比较。
5. 降级处理：标记无效、降低权重、停止任务或请求人工接管。

不要直接把异常值替换成上一帧并假装数据正常。下游必须知道数据已经降级，否则估计器可能继续积累错误信息。

### 7.12 传感器健康监测

生产系统应给传感器建立健康状态，而不是只在节点崩溃时才发现问题：

```text
正常
  ↓ 频率下降/延迟升高
降级
  ↓ 超时/数据无效
故障
  ↓ 恢复或人工处理
恢复中 → 正常
```

健康监测可以包含：

- 最后一帧到达时间。
- 实际频率和最大间隔。
- 数据有效比例。
- 温度、电压和设备错误码。
- TF 是否可查询。
- 标定版本和参数校验值。
- 当前是否允许导航、抓取或控制继续执行。

例如激光短暂丢帧时可以降低速度并等待恢复；激光长期失联时则应停止需要避障的运动，而不是让 Nav2 继续使用旧障碍数据。

### 7.13 传感器验收与故障注入

传感器验收不能只在“正常开机”场景完成，应主动制造故障：

| 测试 | 观察内容 | 预期行为 |
|---|---|---|
| 拔掉传感器 | Topic、诊断和控制状态 | 超时、告警并进入降级 |
| 遮挡镜头/LiDAR | 有效数据比例和障碍观测 | 标记无效或限制运动 |
| 降低网络带宽 | 延迟、丢帧和队列 | 不使用过时数据 |
| 修改 frame 名称 | TF 查询和显示 | 启动检查失败或明确报错 |
| 修改系统时间/仿真时间 | 时间戳和 TF | 检测回拨或暂停处理 |
| 重启驱动 | 生命周期和数据恢复 | 自动重连或人工确认 |

每次测试都应记录传感器版本、参数、场景、故障注入时间、日志、bag 和恢复结果。

### 7.14 第七章学习验收

完成本章后，至少应能够：

- 说明编码器、IMU、LiDAR、相机、GPS 和力传感器各自的优势与失效模式。
- 区分内参、外参和系统标定，并设计对应验证方法。
- 检查传感器消息的类型、频率、QoS、单位、`frame_id` 和时间戳。
- 解释 `LaserScan`、`PointCloud2`、图像和 `camera_info` 的关键字段。
- 使用采样率、最大间隔、延迟、有效比例和静止噪声评价数据质量。
- 识别时间不同步、外参错误、坐标轴错误、畸变和运动畸变的典型现象。
- 为传感器建立健康状态、超时检测、告警和降级策略。
- 通过遮挡、断线、限带宽和重启驱动完成故障注入测试。

第七章的交付物应包括：一份传感器清单、一张传感器到 `base_link` 的 TF 图、一份内外参和时间同步记录、一组数据质量指标，以及一份传感器故障注入与恢复报告。

## 8. 状态估计与传感器融合

### 8.1 为什么需要估计

单一传感器通常无法同时满足全局准确、局部连续和高频反馈：

- 轮速里程计短期平滑，但会因打滑和轮径误差漂移。
- IMU 高频，但 bias 会积累，长期姿态和位置不可靠。
- LiDAR/视觉可提供环境约束，但频率、遮挡和计算延迟可能较大。
- GPS 能提供全球参考，但室内不可用且可能跳变。

状态估计器要把不同频率、噪声和坐标系的数据融合为可供控制使用的连续状态。

### 8.2 Kalman Filter 的最小模型

线性系统可以写为：

\[
x_k=F_kx_{k-1}+B_ku_k+w_k
\]

\[
z_k=H_kx_k+v_k
\]

其中 `Q` 描述过程噪声，`R` 描述观测噪声。EKF 在当前估计点线性化非线性模型，UKF 通过 sigma points 传播非线性。实际调参时，不要把 `Q` 和 `R` 当成“越小越好”：

- `R` 太小会过度相信传感器，噪声或异常值会把估计拉偏。
- `Q` 太小会过度相信模型，真实运动变化无法及时跟随。
- `Q` 太大或 `R` 太小都可能使输出抖动。

### 8.3 `map -> odom` 与 `odom -> base_link`

建议把职责分开：

```text
轮速/视觉/IMU融合
  → 连续局部状态
  → odom -> base_link

SLAM/AMCL/GPS/全局定位
  → 全局位置修正
  → map -> odom
```

不要让两个 EKF、SLAM 和底盘驱动同时发布同一条 `odom -> base_link`。当机器人跳回地图正确位置时，通常是 `map -> odom` 在修正；如果 `odom` 本身跳变，则需要检查里程计来源或融合配置。

### 8.4 估计系统调试顺序

1. 先单独验证轮速里程计方向和尺度。
2. 再验证 IMU 的轴方向、重力方向和 bias。
3. 再检查各传感器时间戳和 TF。
4. 再启用融合，观察位置、速度、姿态和协方差曲线。
5. 最后加入全局定位或 SLAM，验证 `map -> odom` 的修正是否平滑。

### 8.5 状态、观测和过程模型

状态估计首先要定义“想估计什么”。移动机器人常见状态向量可以包含：

\[
x=\begin{bmatrix}
x & y & \theta & v_x & v_y & \omega & b_{a_x} & b_{a_y} & b_{\omega_z}
\end{bmatrix}^{T}
\]

具体状态不必一次包含所有变量，应根据传感器和任务选择。状态过少无法表达真实运动，状态过多则可能难以观测、计算量增加或引入不必要的不稳定性。

每个观测都要说明它约束哪些状态：

| 观测 | 主要约束 | 典型问题 |
|---|---|---|
| 轮速里程计 | 局部速度和相对位姿 | 打滑、比例误差、重复信息 |
| IMU 角速度 | 角速度和姿态变化 | bias、振动、轴方向 |
| IMU 加速度 | 运动变化和重力方向 | 重力处理、噪声和 bias |
| 视觉里程计 | 相对位姿和速度 | 光照、特征不足、尺度 |
| GPS/RTK | 全局位置和航向辅助 | 跳变、多路径、失锁 |
| LiDAR/视觉定位 | 地图中的全局位姿 | 动态障碍、退化环境、延迟 |

过程模型描述“如果没有新观测，机器人根据控制和物理规律会怎样运动”；观测模型描述“当前传感器读数与状态之间有什么关系”。滤波器不是自动理解传感器，而是依赖这些模型和协方差。

### 8.6 贝叶斯滤波的预测与更新

状态估计可以理解为两步循环：

```text
上一时刻后验状态
        ↓ 过程模型 + 控制输入
预测状态和预测协方差
        ↓ 新的传感器观测
计算观测残差和观测可信度
        ↓
更新状态和协方差
        ↓
输出当前估计
```

预测阶段回答“按照模型现在大概在哪里”，更新阶段回答“传感器观测与预测差多少，应该相信谁”。当没有观测时，估计器应继续预测但不应假装不确定性没有增加；因此协方差通常会随时间增长。

线性 Kalman Filter 的核心形式为：

\[
\hat{x}_{k|k-1}=F_k\hat{x}_{k-1|k-1}+B_ku_k
\]

\[
P_{k|k-1}=F_kP_{k-1|k-1}F_k^T+Q_k
\]

观测更新时：

\[
K_k=P_{k|k-1}H_k^T(H_kP_{k|k-1}H_k^T+R_k)^{-1}
\]

\[
\hat{x}_{k|k}=\hat{x}_{k|k-1}+K_k(z_k-H_k\hat{x}_{k|k-1})
\]

其中 `K` 是 Kalman 增益，`z-Hx` 是观测残差。直观上，预测越不确定或观测越可靠，更新就越偏向观测；反之则更多保持模型预测。

### 8.7 EKF、UKF 与粒子滤波的选择

| 方法 | 适合场景 | 优点 | 局限 |
|---|---|---|---|
| KF | 线性模型和近似线性观测 | 简单、高效、易分析 | 无法直接处理明显非线性 |
| EKF | 移动机器人、IMU/里程计融合 | 工程成熟、计算量适中 | 依赖线性化，初值差时可能失效 |
| UKF | 非线性较强、模型难求导 | 不需要显式求雅可比 | 计算量更高，仍依赖合理模型 |
| 粒子滤波 | 多峰分布、全局定位 | 可表示多个假设 | 粒子数和计算量较大，易退化 |

在移动机器人中，EKF 常用于连续里程计和 IMU 融合，粒子滤波常用于已知地图中的全局定位。选择算法前，先确认输入数据、坐标系、时间和噪声是否可信；更复杂的滤波器不能替代错误的外参和时间同步。

### 8.8 协方差的工程调参

过程噪声 `Q` 与观测噪声 `R` 应对应实际不确定性：

- `Q` 大：认为运动模型不够可靠，允许预测快速改变。
- `Q` 小：认为模型稳定，输出更平滑但可能跟不上真实变化。
- `R` 大：认为观测噪声大，滤波器较少相信它。
- `R` 小：认为观测准确，观测会更强地拉动估计。

调参时不要同时把全部协方差缩小。推荐流程：

1. 先单独记录各传感器静止和运动数据。
2. 根据实际方差设置初始观测噪声。
3. 逐个启用传感器，观察状态跳变、延迟和协方差。
4. 比较估计轨迹与独立参考，不要只看输出是否平滑。
5. 注入异常值、短时断线和传感器恢复，验证滤波器是否合理降级。

常见错误是把未提供的状态协方差全部填成零，或者把传感器不观测的状态误设为极小噪声。未知并不等于精确，未观测也不等于可以随意约束为零。

### 8.9 `robot_localization` 的双滤波器思路

移动机器人常采用局部 EKF 和全局 EKF 分工：

```text
轮速 odom + IMU + 视觉里程计
        ↓
局部 EKF
        ↓
odom -> base_link

局部状态 + GPS/AMCL/SLAM 全局观测
        ↓
全局 EKF 或定位节点
        ↓
map -> odom
```

配置时应明确每个输入是否提供：

- 位置、姿态、线速度、角速度或加速度。
- 绝对测量还是相对测量。
- 是否使用差分模式。
- 消息的 frame 和 child frame。
- 输入数据是否已经被另一个滤波器处理。

不要把同一条信息通过多个路径重复融合。例如底盘发布的 odom 已经由轮速和 IMU 融合，再把原始轮速、融合后的 odom 和同一 IMU 以不清晰的协方差全部输入，可能造成相关性被错误忽略和估计过度自信。

### 8.10 观测残差、创新和异常值

观测更新前应关注残差：

\[
\nu_k=z_k-H_k\hat{x}_{k|k-1}
\]

残差长期偏大可能表示：

- 外参或坐标轴错误。
- 传感器时间戳不一致。
- 过程模型不匹配真实运动。
- 协方差配置过小。
- 传感器出现异常或环境退化。

工程系统可以使用门限、马氏距离或连续一致性检查拒绝明显异常观测。拒绝观测后要记录原因和计数，不能静默丢弃，否则现场只能看到“定位偶尔不好”，却无法知道是哪一路数据被拒绝。

### 8.11 可观测性与传感器互补

并不是状态向量中的每个变量都能被当前传感器观测。例如仅靠轮速和 IMU，绝对位置会漂移；仅靠 GPS，短时间局部速度和姿态可能不够平滑；仅靠加速度积分，bias 会快速积累。

传感器融合应关注互补关系：

```text
编码器：短期相对运动
IMU：高频动态变化
视觉/LiDAR：环境几何约束
GPS/RTK：长期全局参考
```

如果加入一个传感器后结果明显变差，首先检查它是否真正提供了新的独立信息，以及时间、坐标和协方差是否正确，而不是默认“传感器越多越好”。

### 8.12 状态估计的 ROS 2 观测清单

运行估计器时，建议同时观察：

```bash
ros2 node info /ekf_filter_node
ros2 topic echo /odometry/filtered --once
ros2 topic hz /odometry/filtered
ros2 run tf2_ros tf2_echo odom base_link
ros2 topic echo /diagnostics
```

离线分析时记录：

- 原始输入和融合输出的时间轴。
- 位置、速度、姿态和角速度曲线。
- pose/twist covariance 的变化。
- 观测残差、拒绝次数和输入超时。
- `map -> odom` 与 `odom -> base_link` 是否分别连续。
- 估计器启动、重置、暂停和恢复时的状态。

### 8.13 常见现象与排查方向

| 现象 | 优先排查 |
|---|---|
| 估计输出抖动 | `R` 过小、输入噪声、时间戳抖动、重复融合 |
| 输出明显滞后 | 队列过深、处理频率不足、时间同步或滤波延迟 |
| 启动后姿态快速翻转 | IMU 轴方向、重力处理、四元数或初始姿态 |
| 位置逐渐漂移 | 缺少全局观测、轮滑、bias 或过程模型错误 |
| 加入 GPS 后跳变 | GPS 多路径、坐标投影、协方差过小或时间延迟 |
| `map -> odom` 不稳定 | 全局定位、TF、地图匹配或重复发布 |
| 协方差越来越小但实际误差变大 | 过度自信、重复融合、`R/Q` 不合理 |
| 传感器恢复后状态突跳 | 旧数据回放、时间回拨、恢复时未清理缓存 |

### 8.14 从零完成一次融合实验

建议按以下阶段搭建，而不是一开始接入所有传感器：

1. 只使用轮速 odom，验证位置、速度和 TF 连续。
2. 加入 IMU 角速度，观察旋转时姿态和角速度响应。
3. 加入 IMU 加速度，检查重力和 bias 配置。
4. 加入视觉或 LiDAR 相对位姿，验证漂移是否受约束。
5. 加入 GPS、AMCL 或 SLAM 全局观测，验证 `map -> odom` 修正。
6. 断开每一路输入，观察系统是否按预期降级。

每个阶段都保留单独参数文件和 rosbag，确保能回答“是哪一路观测改变了结果”。

### 8.15 第八章学习验收

完成本章后，至少应能够：

- 定义移动机器人状态向量、过程模型和观测模型。
- 解释 Kalman Filter 的预测、更新、`Q`、`R`、协方差和残差。
- 说明 KF、EKF、UKF 和粒子滤波的适用边界。
- 根据传感器噪声和实际数据制定初始协方差，而不是盲目缩放参数。
- 解释局部 EKF、全局定位以及 `map -> odom`、`odom -> base_link` 的分工。
- 识别重复融合、观测不可观、时间延迟和异常值带来的问题。
- 使用 Topic、TF、诊断、曲线和 rosbag 检查状态估计质量。
- 完成一次从轮速、IMU 到全局定位的逐步融合实验。

第八章的交付物应包括：一份状态向量和传感器观测表、一份 `Q/R` 参数解释、局部/全局 TF 架构图、一次观测残差分析，以及一份断线和异常值故障测试报告。

## 9. SLAM 与定位

### 9.1 SLAM、定位和建图的区别

- **建图**：构建环境地图。
- **定位**：在已有地图中估计机器人位姿。
- **SLAM**：同时估计机器人轨迹和地图。

不要在固定地图定位模式下同时启动会改写地图的 SLAM 节点，也不要在没有可信里程计和 TF 的情况下期待 SLAM 自动修复所有问题。

### 9.2 2D 激光 SLAM 的基本流程

```text
激光扫描 + 里程计 + TF
        ↓
扫描匹配 / 位姿预测
        ↓
局部地图更新
        ↓
回环检测和图优化
        ↓
地图发布与保存
```

SLAM 的效果依赖环境结构、扫描质量、运动速度、里程计初值、外参和时间同步。长走廊、重复纹理、玻璃、动态人群和大面积空旷区域都可能使匹配退化。

### 9.3 `slam_toolbox` 与 AMCL 的定位

`slam_toolbox` 适合 ROS 2 中的二维建图、继续建图和定位工作流；AMCL 更适合在已保存的静态地图上进行粒子滤波定位。实际选择应根据场景和数据链路决定，而不是认为某一个算法在所有环境都最好。

验收指标应包括：

- 闭环后地图是否出现明显重影。
- 起点回到原处时位姿误差是否可接受。
- 机器人旋转时激光和地图是否稳定。
- 动态障碍是否被错误写入永久地图。
- 地图分辨率、原点、占据阈值和未知区域语义是否正确。

### 9.4 SLAM 的前端、后端和回环

SLAM 通常分成三个相互配合的部分：

```text
传感器和里程计
        ↓
前端：数据关联、扫描匹配、视觉特征和局部位姿
        ↓ 约束/位姿边
后端：位姿图优化、状态估计和地图一致性
        ↑
回环检测：识别“曾经到过这里”并添加全局约束
```

- **前端**负责从连续传感器数据中估计相邻时刻的相对运动，要求实时和鲁棒。
- **后端**负责综合历史约束，优化整条轨迹和地图，通常更关注全局一致性。
- **回环检测**负责发现长期累计的漂移，并通过新的约束修正历史轨迹。

没有回环时，机器人可能在局部看起来运动平滑，但回到起点后地图无法闭合；回环错误时，优化器可能把地图拉扯成错误形状。因此回环检测不是越积极越好，需要结合几何验证和环境特征确认。

### 9.5 地图、轨迹与坐标系

SLAM 系统同时维护三类对象：

| 对象 | 含义 | 常见形式 |
|---|---|---|
| 轨迹 | 机器人在各时刻的位姿估计 | 位姿序列、位姿图 |
| 地图 | 环境结构或占据状态 | Occupancy Grid、点云、特征地图 |
| 坐标关系 | 传感器、机器人和全局地图的变换 | TF、位姿图约束 |

二维导航中常用栅格地图，每个栅格表示空闲、占据或未知；三维感知还可能使用点云、体素、TSDF、特征点或语义地图。地图分辨率越高不一定越好：它会增加存储、计算和对传感器噪声的敏感性。

建图时要明确：

- 地图原点和分辨率。
- 占据阈值和自由空间阈值。
- 未知区域是否允许规划进入。
- 地图是否包含动态障碍、玻璃或临时物体。
- 地图坐标系和 `map -> odom` 的发布责任。

### 9.6 2D LiDAR SLAM 的输入条件

2D 激光 SLAM 通常至少需要：

```text
LaserScan
  + 稳定的 odom -> base_link
  + base_link -> laser 的正确 TF
  + 一致的时间戳和 ROS 时间
  + 适合扫描匹配的环境结构
```

激光扫描平面应尽量稳定、无遮挡，传感器安装不能在机器人运动时产生明显松动。输入速度过快会增加相邻扫描差异和运动畸变；输入速度过慢又可能导致匹配不稳定或地图采集效率过低。

建图前检查：

```bash
ros2 topic hz /scan
ros2 topic echo /scan --once
ros2 run tf2_ros tf2_echo base_link laser
ros2 topic hz /odom
```

若激光 frame、机器人 frame 或 odom 方向错误，SLAM 可能仍然输出地图，但地图会出现重影、倾斜、拉伸或周期性错位。

### 9.7 推荐的建图工作流

建图不是“启动节点后随便走一圈”。建议按以下阶段执行：

1. **准备场景**：清理会移动的物体，确认边界、通道和关键区域。
2. **验证底层输入**：先检查激光、odom、TF、时间和 QoS。
3. **慢速探索**：沿外墙、走廊和房间边界移动，保持足够重叠观测。
4. **闭环验证**：回到已知区域，观察回环是否稳定、地图是否闭合。
5. **补采关键区域**：检查窄门、转角、低矮障碍和大面积空旷区域。
6. **保存地图**：记录地图分辨率、原点、阈值、文件和软件版本。
7. **独立验证**：停止建图，以保存的地图执行定位或导航。

探索路径应尽量提供几何约束，避免长时间只在一条重复走廊或大面积空旷区域直行。旋转和转弯时保持合理速度，减少激光匹配和时间同步的压力。

### 9.8 地图质量检查

一张能被保存的地图不一定是可导航地图。检查时至少关注：

- 墙体是否连续，是否有明显双墙或重影。
- 起点和回环处是否闭合。
- 门口、走廊和转角宽度是否与实际一致。
- 动态人员和临时物体是否被写成永久障碍。
- 激光盲区、玻璃和反光表面是否造成错误空洞。
- 地图边界外未知区域是否被错误当成自由空间。
- 地图分辨率是否能表达机器人 footprint 和最窄通道。

可以用实际测量的墙间距离、起点回环误差和多次定位结果作为量化指标，而不是只凭 RViz2 中“看起来比较直”。

### 9.9 已知地图定位与 AMCL

在已保存的二维地图中，AMCL 常用粒子表示机器人可能的位姿分布：

```text
初始位姿和粒子集合
        ↓ 里程计运动更新
粒子预测
        ↓ 激光与地图匹配
粒子权重更新
        ↓ 重采样
机器人位姿估计和 map -> odom
```

AMCL 的效果依赖地图质量、激光模型、里程计连续性、初始位姿和机器人运动。初始位姿离真实位置太远、地图中存在大量重复结构、激光安装外参错误或 odom 跳变，都可能导致粒子无法收敛或收敛到错误位置。

定位启动时应记录：

- 地图文件和地图参数版本。
- 初始位姿来源和误差范围。
- 激光 frame、地图 frame 和 base frame。
- 里程计的连续性和速度限制。
- 定位收敛时间、协方差和重定位策略。

### 9.10 SLAM、AMCL 与全局定位的选择

| 需求 | 合适方向 | 主要前提 |
|---|---|---|
| 首次构建环境地图 | SLAM | 激光/视觉、odom、TF 和可观测环境 |
| 在固定地图中运行 | AMCL 或其他定位器 | 地图质量和初始位姿可用 |
| 地图会持续变化 | 增量建图或动态地图方案 | 明确动态物体和地图更新策略 |
| 室外大范围全局参考 | GPS/RTK + 局部估计 | 坐标投影、失锁和多路径处理 |
| 多传感器高精度定位 | LiDAR/视觉/GPS 融合 | 外参、时间和协方差可信 |

不要同时让建图节点、静态地图定位节点和多个全局定位器争夺同一条 TF。先确定当前系统处于“建图”“固定地图定位”还是“全局融合”模式，再启动对应组件。

### 9.11 动态环境与地图维护

真实环境不是静态的。人员、车辆、门、箱子和家具会让 SLAM 与定位面对动态观测。处理策略包括：

- 选择更稳定的墙体、柱子和固定结构作为匹配特征。
- 使用传感器过滤、地面分割或动态目标检测。
- 不把短时障碍直接写入永久地图。
- 为地图设置版本、适用区域和过期条件。
- 环境发生较大变化时重新建图或局部更新。

如果机器人在动态人群中定位变差，不一定是滤波器参数问题，也可能是当前观测不满足静态环境假设。应通过场景对比区分算法退化与环境变化。

### 9.12 SLAM/定位常见失败模式

| 现象 | 优先检查 |
|---|---|
| 地图整体拉伸 | 里程计尺度、轮径、时间同步和运动速度 |
| 墙体出现双影 | 外参、扫描匹配、轮滑和动态障碍 |
| 回到起点无法闭环 | 环境重复、回环阈值、观测重叠和时间 |
| 地图突然扭曲 | 错误回环、TF 跳变或传感器异常 |
| AMCL 一直不收敛 | 初始位姿、地图质量、激光 frame 和粒子数量 |
| 定位在相似房间间跳转 | 环境可观测性不足、地图重复结构 |
| 机器人移动后地图不更新 | Topic、QoS、时间、TF 或 SLAM 节点状态 |
| 地图中出现大量人影 | 动态环境、扫描过滤和建图速度 |

排查顺序仍应是：传感器数据 → 时间戳 → 外参 TF → odom → 算法参数 → 地图和回环。不要先通过调大回环权重或粒子数量掩盖输入问题。

```

```

## 10. Nav2 导航系统

### 10.1 Nav2 的分层结构

Nav2 是一组通过 ROS 2 Action、Topic、TF、参数和插件协作的导航服务器。典型链路为：

```text
NavigateToPose Action
        ↓
BT Navigator
        ↓
Planner Server → Global Path
        ↓
Controller Server → Velocity Command
        ↓
底盘控制器 → Odometry
        ↘ Local Costmap / Sensors

Localization → map -> odom
Odometry     → odom -> base_link
```

核心角色：

- `Planner Server`：根据全局地图和目标生成全局路径。
- `Controller Server`：根据路径、局部代价地图和运动学约束生成控制命令。
- `Behavior Server`：处理清图、旋转、后退等恢复或行为插件。
- `BT Navigator`：使用 Behavior Tree 协调导航任务、反馈、恢复和取消。
- `Costmap Server`：维护静态层、障碍层、膨胀层和过滤器。
- `Smoother Server`：对路径进行平滑，减少尖角和不必要的旋转。
- `Lifecycle Manager`：按确定顺序配置和激活关键服务器。

### 10.2 全局规划和局部控制

全局规划关心“从起点到目标的整体可行路线”，常见方法包括基于栅格搜索的 NavFn/A*、Smac Planner 和基于路线图的 Route Server。局部控制关心“当前时刻怎样安全地跟踪路线”，需要处理实时障碍、速度和加速度约束、底盘运动学以及目标附近的收敛。

全局路径可行不代表机器人一定能走：路径可能过于尖锐、离障碍太近、曲率超出底盘能力，或局部代价地图根本没有收到传感器数据。

### 10.3 代价地图

二维代价地图通常由以下层组成：

1. `StaticLayer`：静态地图。
2. `ObstacleLayer` 或 `VoxelLayer`：实时障碍和点云。
3. `InflationLayer`：按机器人安全距离扩张障碍代价。
4. `Keepout`、速度区等过滤器：对区域施加禁止进入或速度限制。

最重要的参数不是“看起来能跑”的默认值，而是：

- `resolution` 是否与地图和传感器精度匹配。
- `robot_radius` 或 `footprint` 是否覆盖真实外廓。
- 激光的 `obstacle_min_range`、`obstacle_max_range` 是否正确。
- `raytrace` 是否能清除已离开的障碍。
- `transform_tolerance` 是否与系统延迟匹配。
- 膨胀半径是否包含刹车距离和定位误差，而不只是几何半径。

### 10.4 MPPI 的理解

MPPI 是一种基于采样和滚动时域的模型预测控制方法。每次控制周期以当前控制序列为中心采样大量带噪声的候选序列，根据运动模型向前预测轨迹，再用代价函数评价路径跟踪、避障、目标收敛、速度限制等目标，最后对候选控制进行加权更新并只执行第一步。

```text
当前状态和上一周期控制序列
        ↓
采样控制扰动
        ↓
运动模型 rollout
        ↓
critics 计算轨迹代价
        ↓
按代价加权更新控制序列
        ↓
校验最优轨迹 → 执行第一拍控制
```

调 MPPI 不应只修改 `batch_size`。应按以下顺序：

1. 确认底盘运动模型、速度和加速度限制正确。
2. 确认局部代价地图、footprint 和障碍物观测可信。
3. 设置预测时长和时间步，使其覆盖有意义的运动距离。
4. 调整路径跟踪、路径对齐、目标和障碍 critic 的权重。
5. 再平衡采样规模、温度、噪声和计算耗时。
6. 最后验证轨迹校验、碰撞检查、速度死区和 fallback。

典型现象与方向：

| 现象 | 优先检查 |
|---|---|
| 机器人原地抖动 | 速度死区、控制频率、角度 critic、底盘 PID |
| 路径跟踪偏差大 | 里程计、预测时长、PathFollow/Align 权重 |
| 障碍前不停车 | 传感器 QoS、局部 costmap、footprint、碰撞阈值 |
| 计算占满 CPU | batch、时间步、可视化、点云分辨率 |
| 到目标附近绕圈 | Goal/GoalAngle、停止速度、目标容差、角度定义 |

### 10.5 Nav2 调参总原则

调参顺序应从底层到上层：

```text
TF 和时间
  → 传感器 Topic/QoS
  → 里程计和底盘闭环
  → 地图与 costmap
  → footprint 和物理限制
  → 全局规划
  → 局部控制器
  → 行为树与恢复
  → 性能和安全验收
```

一次只改变少数相关参数，记录场景、地图、版本、参数和结果。否则即使成功，也无法知道真正起作用的因素。

### 10.6 Global Costmap 与 Local Costmap

全局代价地图和局部代价地图服务于不同决策：

| 项目 | Global Costmap | Local Costmap |
|---|---|---|
| 主要范围 | 覆盖更大区域或整张地图 | 机器人周围滚动窗口 |
| 主要输入 | 静态地图、禁行区和全局障碍 | 激光、点云、动态障碍 |
| 主要消费者 | 全局规划器 | 局部控制器和碰撞检查 |
| 更新关注点 | 地图一致性和路线可达性 | 实时性、延迟和障碍清除 |
| 常见问题 | 地图原点、分辨率、未知区 | 传感器 QoS、TF、窗口和更新频率 |

局部代价地图即使没有静态地图，也可以根据传感器维护机器人附近障碍；全局代价地图则需要稳定的地图或全局环境表示。两者都必须使用与机器人和传感器兼容的 frame，并明确是否使用 rolling window。

### 10.7 Footprint、膨胀和安全距离

`robot_radius` 适合近似圆形底盘；非圆形底盘、带托盘或带机械臂的机器人应使用多边形 `footprint`。footprint 只描述几何外廓，不自动包含定位误差、刹车距离、传感器延迟和机械摆动。

实际安全边界可以理解为：

```text
几何外廓
  + 定位误差
  + 传感器和控制延迟造成的运动距离
  + 制动距离
  + 结构/载荷摆动余量
  = 实际安全边界
```

膨胀层的意义不是简单“让障碍变大”，而是让规划器和控制器在接近障碍时逐渐增加代价，促使机器人保持合理间距。膨胀半径过小会贴墙甚至碰撞，过大则可能让窄门不可通行。

### 10.8 Planner 与 Controller 的选择

全局规划器和局部控制器要与底盘模型、地图结构和任务目标匹配：

| 模块 | 适合关注 | 选择依据 |
|---|---|---|
| 栅格搜索规划器 | 静态地图中的可达路线 | 地图分辨率、未知区和路径平滑 |
| 运动学规划器 | 转弯半径、车辆模型和倒车 | 底盘约束、曲率和方向 |
| 纯跟踪类控制器 | 简洁、低计算量的路径跟踪 | 速度、路径曲率和前视距离 |
| 采样/MPC 类控制器 | 多约束、动态障碍和轨迹优化 | CPU、预测时域、代价设计 |
| 反应式控制器 | 快速响应局部障碍 | 传感器频率、稳定性和避障边界 |

选择控制器时不要只比较“能否到达”。还要比较：

- 路径跟踪误差。
- 最小障碍距离。
- 停止距离和最大速度。
- 计算时间和 CPU 占用。
- 动态障碍出现时的响应延迟。
- 窄门、急转弯、倒车和目标附近的行为。

### 10.9 行为树与恢复行为

Nav2 的行为树通常把导航任务拆成条件、动作和控制节点：

```text
开始导航
  ↓
检查定位和系统状态
  ↓
规划全局路径
  ↓
跟踪路径
  ├── 成功 → 到达目标
  ├── 规划失败 → 清理地图/重新规划
  ├── 控制失败 → 停止/旋转/后退
  └── 定位或传感器故障 → 降级并请求人工处理
```

理解行为树时重点看：

- `Sequence`：前一步成功后才执行下一步。
- `Fallback`：主策略失败时尝试备选策略。
- `Reactive` 结构：每次 tick 重新检查条件。
- `RecoveryNode`：失败后执行恢复，再决定是否重试。
- `RateController`：限制某些检查或重规划的频率。

恢复行为不能无限循环。每个恢复策略都应有最大次数、超时和最终失败状态；否则机器人可能在障碍前反复旋转、清图或重规划。恢复行为也不能绕过急停、限速和碰撞监控。

### 10.10 Lifecycle 与 Nav2 Bringup

Nav2 启动顺序通常需要满足依赖关系：

```text
机器人描述和 TF
        ↓
传感器与 odom
        ↓
地图/定位
        ↓
Costmap
        ↓
Planner/Controller/Behavior Server
        ↓
BT Navigator 和任务接口
```

节点处于 `active` 不代表整个链路已经可用。启动验收应分别确认：

```bash
ros2 lifecycle get /map_server
ros2 lifecycle get /planner_server
ros2 lifecycle get /controller_server
ros2 action list -t
ros2 node list
```

如果启动失败，不要先修改所有参数。先确认失败节点、生命周期转移、参数文件路径、插件加载、依赖 Topic 和 TF 是否满足，再处理上层节点。

### 10.11 最小 Nav2 bringup 验证

建议把导航验证拆成四个闭环：

#### 闭环一：定位

确认机器人在地图中的初始位姿正确，`map -> odom -> base_link` 连续，激光与地图重合。

#### 闭环二：代价地图

确认静态地图显示、实时障碍进入 local costmap、障碍离开后能够清除，footprint 与真实机器人一致。

#### 闭环三：规划

发送一个近距离、无障碍目标，确认 Planner Server 返回路径，路径不穿过静态障碍且满足底盘基本约束。

#### 闭环四：控制

确认 Controller Server 生成速度，底盘执行后 odom 更新，局部轨迹与实际运动一致，目标附近能够停止。

只有四个闭环都通过后，才进入动态障碍、多目标点、恢复行为和复杂 MPPI 调参。

### 10.13 常见导航故障与分层排查

| 现象 | 排查层次 |
|---|---|
| 目标发送后无反应 | Action Server、Lifecycle、BT XML、目标 frame |
| Planner 无路径 | 起点/目标合法性、地图、全局 costmap、footprint |
| Local Costmap 没障碍 | 传感器 Topic、QoS、frame、TF、观察源配置 |
| 机器人贴墙或穿墙 | footprint、膨胀半径、定位误差、障碍清除 |
| 机器人原地转圈 | odom、目标角度、控制器 critic、速度死区 |
| 机器人走走停停 | 控制频率、命令超时、局部规划失败、速度限制 |
| 动态障碍前不停车 | 传感器延迟、costmap 更新、碰撞监控和刹车距离 |
| 窄门无法通过 | 地图尺度、footprint、膨胀半径、规划器约束 |
| 恢复行为无限循环 | BT RecoveryNode、重试次数、故障根因未修复 |
| CPU 占用过高 | 代价地图分辨率、点云、MPPI 采样规模、可视化 |

排查原则是一次只回答一个问题：输入有没有、坐标对不对、时间新不新、节点是否 active、输出是否合理、底盘是否执行。不要同时更换地图、控制器、速度和所有 costmap 参数。

### 10.14 导航性能与安全指标

导航验收应从“能到达”扩展为可量化指标：

| 指标 | 说明 |
|---|---|
| 任务成功率 | 指定场景和目标下成功完成的比例 |
| 到达时间 | 从目标发送到满足位置/角度容差的时间 |
| 路径长度 | 实际轨迹与全局路径的长度比较 |
| 跟踪误差 | 横向误差、角度误差和目标误差 |
| 最小障碍距离 | 运行过程中与障碍物的最小间距 |
| 停止距离 | 急停、传感器异常或目标停止时的距离 |
| 恢复次数 | 清图、旋转、后退和重规划的次数 |
| 计算资源 | Planner/Controller 周期、CPU、内存和延迟 |
| 故障恢复率 | 传感器、定位或网络故障后的安全恢复比例 |

测试场景至少包含：空旷区域、窄门、急转弯、动态障碍、局部遮挡、定位初始误差、目标不可达、传感器短时丢帧和控制命令失联。

- 阅读行为树中的 Sequence、Fallback、Recovery 和重规划逻辑。
- 按定位、代价地图、规划、控制四个闭环完成最小导航验证。
- 使用 RViz2、CLI、Foxglove 和 rosbag2 量化导航问题。
- 设计包含动态障碍、传感器失联、定位误差和急停的导航验收测试。

第十章的交付物应包括：一份 Nav2 节点和接口图、一份 costmap/footprint 参数说明、一份行为树或恢复策略说明、一次最小导航实验记录，以及一份包含成功率、误差、障碍距离和故障恢复的验收报告。

## 11. 机械臂、运动学与 MoveIt 方向

### 11.1 正运动学

给定关节变量 `q`，通过各关节的刚体变换得到末端位姿：

\[
T_{0n}(q)=T_{01}(q_1)T_{12}(q_2)\cdots T_{n-1,n}(q_n)
\]

传统 DH 参数有助于系统建立链式模型，但工程中仍要回到实际 URDF 的 joint origin、axis 和 frame 定义。正运动学能回答“给定关节角，末端在哪里”，不能直接回答“末端到目标应怎样走”。

### 11.2 逆运动学与 Jacobian

逆运动学根据目标位姿求关节变量，可能有多解、无解、奇异位形和关节限位。Jacobian 建立关节速度与末端速度之间的关系：

\[
\dot{x}=J(q)\dot{q}
\]

当 `J` 接近奇异时，末端某些方向的运动能力会下降，关节速度可能变得很大。实际规划要同时考虑碰撞、关节范围、速度、加速度、轨迹连续性和工具姿态。

### 11.3 机械臂学习顺序

```text
坐标系与旋转
  → URDF/Xacro 和 joint limits
  → FK/IK/Jacobian
  → 碰撞模型和自碰撞矩阵
  → MoveIt 规划场景
  → Trajectory Controller
  → 夹爪与任务状态机
  → 力控、视觉伺服和真实硬件
```

机械臂的规划成功不代表执行成功。必须检查轨迹时间参数化、控制器接口、关节反馈、急停、软限位和工具碰撞区域。

### 11.4 机械臂的坐标链和任务对象

一个可执行的机械臂任务通常包含以下坐标和对象：

```text
世界/工作台 frame
        ↓
机器人基座 base_link
        ↓
关节和连杆链
        ↓
腕部/法兰 frame
        ↓
工具中心点 TCP
        ↓
目标物体、抓取姿态和放置姿态
```

必须区分：

| 对象 | 含义 |
|---|---|
| `base_link` | 机械臂基座参考系 |
| `flange` | 末端法兰，通常是机械安装接口 |
| `tool0`/TCP | 工具中心点，随夹具或工具变化 |
| `planning_frame` | MoveIt 规划使用的参考坐标系 |
| `end_effector_link` | 规划组中的末端 link |
| `object` | Planning Scene 中的碰撞物体 |

工具更换后，TCP 的位置和姿态可能改变；如果仍使用旧 TCP，机械臂可能“姿态看似正确但夹爪位置错误”。视觉目标也必须说明是在相机坐标系、基座坐标系还是世界坐标系中表达。

### 11.5 正运动学、逆运动学与解的选择

正运动学是确定性的：给定一组关节变量，通常可以直接计算末端位姿。逆运动学则可能存在：

- 多组解，例如肘上/肘下、腕部翻转和不同绕行姿态。
- 无解，目标超出工作空间或姿态约束不可满足。
- 无穷近似解，冗余机械臂可以用不同姿态完成同一任务。
- 受限解，关节限位、碰撞、工具方向和速度约束排除部分解。

逆解选择不能只看“是否到达目标”，还要比较：

| 评价项 | 作用 |
|---|---|
| 与当前关节状态的距离 | 避免突然跳到另一组解 |
| 关节限位余量 | 远离边界，保留后续运动空间 |
| 碰撞风险 | 避免自碰撞和环境碰撞 |
| 奇异性指标 | 避免末端运动能力突然下降 |
| 轨迹连续性 | 减少速度和加速度突变 |
| 任务姿态 | 满足抓取、焊接、插装等工艺要求 |

### 11.6 DH 参数、URDF 与实际模型

DH 参数适合用表格描述理想化的串联运动链；URDF 则通过 joint origin、axis、parent 和 child 描述工程模型。两者可以互相帮助理解，但不能直接假设参数一一对应。

建立机械臂模型时建议：

1. 先根据实物定义每个 joint 的正方向和零位。
2. 用简单几何和已知尺寸验证 FK。
3. 对比 URDF 计算的末端位姿和实测位置。
4. 再加入 visual、collision、惯性和工具模型。
5. 最后配置 MoveIt 的 planning group、末端和碰撞矩阵。

如果 DH 模型与 URDF 结果不一致，优先检查坐标原点、轴方向、零位偏置和旋转顺序，而不是直接给末端增加一个“经验修正”。

### 11.7 Jacobian、奇异位形与可操作度

Jacobian 将关节速度映射到末端线速度和角速度：

\[
\begin{bmatrix}v\\\omega\end{bmatrix}
=J(q)\dot{q}
\]

当 Jacobian 降秩或接近奇异时，机械臂可能出现：

- 末端某个方向几乎无法运动。
- 为实现很小的末端速度，需要很大的关节速度。
- 关节速度、力矩或控制噪声突然放大。
- 规划器难以找到平滑轨迹。

常见奇异场景包括腕部轴线重合、手臂完全伸直或多个关节形成特殊几何关系。规避方法包括：

- 在规划代价中远离奇异区域。
- 使用阻尼最小二乘求解速度：

\[
\dot{q}=J^T(JJ^T+\lambda^2I)^{-1}\dot{x}
\]

- 限制关节速度和加速度。
- 通过冗余自由度改变肘部或腕部姿态。
- 避免只用末端位置约束而忽略姿态和关节状态。

### 11.8 工作空间、冗余与姿态约束

工作空间不是一个简单球体，它受到连杆长度、关节限位、碰撞、工具尺寸、基座安装、姿态要求和奇异位形共同影响。

| 工作空间类型 | 含义 |
|---|---|
| 可达空间 | 末端至少能到达的位置集合 |
| 灵巧空间 | 末端能以足够多姿态到达的位置集合 |
| 无碰撞空间 | 同时满足环境和自碰撞约束的位置集合 |
| 工艺空间 | 满足任务姿态、速度、力和精度要求的区域 |

冗余机械臂可以在保持末端任务的同时调整肘部、避开障碍、远离限位或优化可操作度。规划时要明确主任务和次任务，例如：

```text
主任务：保持 TCP 沿目标轨迹运动
次任务：远离关节限位、避开奇异点、减少能耗、避开障碍
```

### 11.9 MoveIt 2 的核心组成

MoveIt 2 规划通常涉及：

- `robot_description`：URDF/Xacro 机器人模型。
- SRDF：规划组、虚拟关节、末端执行器和自碰撞配置。
- Planning Scene：机器人状态、世界碰撞物体和允许碰撞矩阵。
- Planning Group：例如 `arm`、`gripper` 或完整机械臂组。
- IK Solver：把末端目标转换为关节目标。
- Planner：搜索或优化无碰撞关节路径。
- Time Parameterization：为路径增加时间、速度和加速度。
- Trajectory Controller：执行 `JointTrajectory` 并反馈关节状态。

规划场景必须与真实环境同步：

```text
机器人模型
  + 当前关节状态
  + 工具和夹具
  + 桌面、墙体和障碍物
  + 抓取物体
  + 允许/禁止碰撞关系
  → 碰撞检测与轨迹规划
```

MoveIt 规划成功只表示在当前模型和 Planning Scene 中找到了一条可行解，不等于真实环境中一定安全。

### 11.10 自碰撞、环境碰撞与碰撞矩阵

碰撞模型需要覆盖真实外廓，但不应因为视觉网格过于复杂而拖慢规划。自碰撞矩阵通常会忽略永远不会相撞或始终接触的 link 对，以减少计算量；这必须通过姿态采样和实物检查验证。

碰撞检查至少包括：

- 连杆之间的自碰撞。
- 机械臂与工作台、地面和护栏的碰撞。
- 末端工具、夹爪和线缆的外廓。
- 被抓取物体与环境的碰撞。
- 规划路径离障碍的最小距离。
- 传感器视野、人的安全区域和软限位。

碰撞模型过小会带来真实碰撞，过大则会产生大量“假碰撞”。应根据实际风险对危险部件保守建模，对不影响安全的细节适度简化。

### 11.11 关节空间与笛卡尔空间轨迹

| 轨迹类型 | 特点 | 适合场景 |
|---|---|---|
| 关节空间轨迹 | 各关节平滑运动，末端路径不一定直线 | 快速点到点、避开复杂区域 |
| 笛卡尔直线轨迹 | 末端沿直线或指定姿态运动 | 插入、焊接、打磨、直线抓取 |
| 圆弧/曲线轨迹 | 末端沿工艺曲线运动 | 喷涂、跟踪、加工 |
| 视觉伺服轨迹 | 根据实时视觉误差更新 | 对准、跟踪、动态抓取 |

轨迹生成后还要进行时间参数化：

```text
几何路径
  → 关节限位检查
  → 速度/加速度/jerk 约束
  → 时间参数化
  → 碰撞和连续性检查
  → 控制器执行
```

如果只检查路径点而没有检查时间参数化，轨迹在点与点之间可能产生过大的速度或加速度。执行前应检查关节位置、速度、加速度、时间间隔和轨迹是否连续。

### 11.12 夹爪、工具与抓取任务

机械臂任务通常不止“移动到目标”：

```text
移动到预抓取姿态
  → 接近目标
  → 闭合夹爪
  → 检查夹爪/力传感器反馈
  → 抬升和搬运
  → 移动到放置姿态
  → 松开并确认物体释放
```

工具和夹爪需要明确：

- TCP 相对法兰的外参。
- 夹爪关节和控制接口。
- 最大开合范围、速度和力。
- 物体碰撞几何和质量。
- 抓取成功、滑落、夹空和卡住的判定。
- 夹爪失电、通信中断和急停时的安全状态。

### 11.13 视觉与手眼标定

相机安装在机器人外部时，常见链路为：

```text
相机 frame → 目标检测/位姿估计
        ↓
相机到基座的外参
        ↓
目标在 base_link/world 中的位姿
        ↓
MoveIt 规划抓取轨迹
```

相机安装在末端时，属于 eye-in-hand；相机固定在工作台或环境中时，属于 eye-to-hand。两者的变换链不同，但都需要：

- 相机内参和畸变参数。
- 相机与机器人之间的外参。
- 目标检测结果的坐标系和时间戳。
- 机器人当前关节状态和末端姿态。
- 标定独立验证和误差指标。

抓取失败时，先区分目标检测误差、手眼外参误差、TCP 误差、机械臂执行误差和物体滑动，而不是统称为“MoveIt 不准”。

### 11.14 机械臂执行安全

真实机械臂首次执行应采用分层保护：

1. 限制关节位置、速度、加速度和力矩。
2. 限制工作空间和工具速度。
3. 低速单步执行，确认每段轨迹。
4. 使用软限位、机械限位、急停和人工接管。
5. 检查规划场景与真实障碍是否一致。
6. 监控关节反馈、跟踪误差、电流、温度和控制器状态。
7. 轨迹执行超时或反馈异常时立即停止，不自动无限重试。

软件碰撞检测不能替代硬件安全回路。夹爪、负载、工具和工作台发生变化时，必须重新评估碰撞、惯性和安全距离。

### 11.15 机械臂调试顺序

建议按“模型 → 状态 → 单关节 → FK → IK → 碰撞 → 轨迹 → 任务”的顺序：

```text
URDF/SRDF 和 TF 正确
  → joint_states 方向、单位、零位正确
  → 单关节低速运动
  → FK 与实测末端位置一致
  → IK 可求解且结果连续
  → Planning Scene 碰撞正确
  → 轨迹时间参数化和控制器反馈正常
  → 夹爪/视觉/任务状态机联调
```

常用观测命令：

```bash
ros2 topic echo /joint_states --once
ros2 topic hz /joint_states
ros2 run tf2_ros tf2_echo base_link tool0
ros2 action list -t
ros2 control list_controllers
ros2 topic echo /joint_trajectory_controller/state --once
```

### 11.16 第十一章学习验收

完成本章后，至少应能够：

- 说明机械臂 base、flange、TCP、planning frame 和 end-effector link 的区别。
- 根据 URDF 或 DH 参数计算正运动学，并解释逆运动学多解、无解和限位。
- 使用 Jacobian 分析末端速度、奇异位形和冗余自由度。
- 区分可达空间、灵巧空间、无碰撞空间和工艺空间。
- 解释 MoveIt 2 中 URDF、SRDF、Planning Scene、IK、Planner 和 Trajectory Controller 的职责。
- 为机械臂配置自碰撞、环境碰撞、工具模型和抓取物体。
- 区分关节空间、笛卡尔空间和视觉伺服轨迹。
- 检查轨迹时间参数化、关节反馈、控制器状态、TCP 和手眼外参。
- 设计低速、限位、急停、超时和人工接管的机械臂安全测试。

第十一章的交付物应包括：一张机械臂坐标链、一份关节和工具参数表、一次 FK/IK 验证、一份 Planning Scene 碰撞检查记录、一条经过时间参数化的轨迹，以及一份真机低速执行和安全测试报告。

## 12. 仿真、ros2_control 与 Sim-to-Real

### 12.1 仿真的正确定位

仿真适合验证：

- 节点连接、Topic、Action、参数和 launch。
- URDF/SDF、TF、碰撞和关节方向。
- 规划算法在可重复场景下的行为。
- 传感器掉线、动态障碍、低电量和故障恢复。
- 代码回归和参数变化的影响。

仿真不能自动证明真机安全。真机仍然存在摩擦变化、轮胎打滑、电机饱和、通信延迟、传感器遮挡、结构弹性、温度、电压和人类行为等差异。

### 12.2 `ros2_control` 的分层

`ros2_control` 把硬件接口、控制器管理和 ROS 2 数据接口分开：

```text
Hardware Interface
├── read()：读取编码器、关节状态、故障
└── write()：输出速度、位置或力矩命令
        ↓
Controller Manager
        ↓
Controllers
├── joint_state_broadcaster
├── diff_drive_controller
├── joint_trajectory_controller
└── 自定义控制器
```

控制器管理器需要关注控制周期、线程抖动、接口声明、生命周期和故障降级。高频控制循环中不能随意执行阻塞 I/O、动态分配或复杂日志操作。仿真控制器和真机控制器应尽量保持相同的 ROS 2 接口，差异封装在硬件层。

### 12.3 Sim-to-Real 清单

- 尺寸单位和坐标轴一致。
- 质量、质心和惯性矩合理。
- 摩擦、阻尼、轮胎接触参数不完全理想化。
- 传感器加入合理噪声、延迟、丢帧和视野限制。
- 控制器使用真实速度、加速度、 jerk 和电流限制。
- 仿真与真机采用相同的 Topic 名称、消息类型和 frame 名称。
- 真机首次测试使用限速、吊架/空载、远程急停和人工接管。

### 12.4 仿真栈的职责边界

一套 ROS 2 机器人仿真通常包含多个层次：

```text
机器人描述：URDF/Xacro
        ↓
仿真模型和世界：SDF/Gazebo
        ↓
物理引擎：碰撞、摩擦、重力、关节约束
        ↓
仿真传感器和插件：LiDAR、IMU、相机、接触传感器
        ↓
ros_gz_bridge 或 ROS 2 插件
        ↓
ROS 2 节点、ros2_control、Nav2、MoveIt 2
```

每一层都有自己的失败模式：

| 层次 | 主要问题 |
|---|---|
| URDF/Xacro | link、joint、TF、惯性和资源路径错误 |
| SDF/world | 模型加载、灯光、地面、物理参数和插件错误 |
| 物理引擎 | 穿模、抖动、滑动、穿透和时间步不稳定 |
| 传感器仿真 | frame、频率、噪声、延迟、视场和量程错误 |
| Bridge/接口 | Topic 类型、方向、QoS 和命名不匹配 |
| 控制器 | 接口不 active、命令方向错误、周期抖动 |
| 上层算法 | `use_sim_time`、TF、参数和生命周期错误 |

排错时不要把“模型显示出来”当作仿真完成。至少要分别验证模型、物理、传感器、控制和上层算法闭环。

### 12.5 Gazebo、SDF 与仿真世界

仿真世界通常包含：

- 地面、墙体、障碍物和可移动物体。
- 光源、相机视角和环境材质。
- 物理引擎、重力和仿真步长。
- 机器人模型、传感器和控制插件。
- 用于测试的初始位姿、目标点和动态障碍。

建议把世界按用途拆分，而不是维护一个越来越大的文件：

```text
worlds/
├── empty.sdf              # 空旷基础验证
├── corridor.sdf           # 走廊和回环
├── warehouse.sdf          # 货架、窄道和动态障碍
└── regression.sdf         # 固定回归场景
models/
├── robot/
├── pallet/
└── obstacle_box/
```

每个回归世界都应固定版本和初始条件。只有场景、模型、参数和随机种子可追踪，仿真结果才具有可比较性。

### 12.6 仿真时间与 `/clock`

仿真算法应使用 ROS 时间，而不是在节点中直接读取操作系统墙上时间。仿真器通常发布 `/clock`，上层节点通过 `use_sim_time` 使用它：

```text
Gazebo 仿真时间
        ↓ /clock
传感器时间戳、TF、控制器、SLAM、Nav2、rosbag
```

检查仿真时钟：

```bash
ros2 topic echo /clock --once
ros2 topic hz /clock
ros2 param get /node_name use_sim_time
```

常见时间问题：

- 仿真器暂停，算法节点一直等待未来时间。
- 只有部分节点设置 `use_sim_time`，导致 TF 和传感器时间不一致。
- 启动时 `/clock` 尚未发布，节点读取到零时间或异常时间。
- 回放 bag 时，节点没有使用 bag 的仿真时间。
- 仿真步长过大，控制周期和传感器周期无法满足要求。

### 12.7 `ros_gz_bridge` 与接口桥接

Gazebo Transport 和 ROS 2 通信不是同一套接口，桥接层负责转换：

```text
Gazebo Transport Topic
        ↔ ros_gz_bridge
ROS 2 Topic/Service
```

桥接时需要明确：

- 方向是 Gazebo → ROS 2、ROS 2 → Gazebo，还是双向。
- 两侧消息类型是否具有相同语义。
- Topic 名称和 namespace 是否一致。
- QoS、队列深度和更新频率是否合适。
- `/clock`、LaserScan、IMU、Image、PointCloud2 和命令接口是否都已桥接。

桥接排查：

```bash
ros2 topic list
ros2 topic type /scan
ros2 topic info /scan --verbose
ros2 topic hz /scan
```

如果 Gazebo 中能看到激光而 ROS 2 中没有 `/scan`，优先检查桥接方向和类型；如果 ROS 2 中有 Topic 但 Nav2 不使用，继续检查 `frame_id`、时间戳、QoS 和 costmap source 配置。

### 12.8 仿真传感器：理想模型与可迁移模型

传感器仿真至少要模拟真实系统中的主要限制：

| 传感器 | 应考虑的仿真因素 |
|---|---|
| LiDAR | 量程、角分辨率、扫描频率、遮挡、噪声、丢帧和安装外参 |
| IMU | bias、白噪声、重力、轴向、频率、延迟和振动 |
| 相机 | 分辨率、视场、曝光、噪声、畸变、延迟和遮挡 |
| 深度相机 | 深度量程、空洞、边缘误差、强光和材质影响 |
| 编码器 | 量化、延迟、打滑、方向错误和轮径误差 |
| 接触/力传感器 | 零偏、饱和、接触噪声和采样频率 |

第一阶段可以使用理想传感器验证接口，第二阶段必须逐步加入噪声、延迟、丢帧、遮挡和模型误差。否则算法可能只在仿真中依赖现实不存在的完美数据。

### 12.9 仿真中的 `ros2_control` 闭环

仿真控制器应尽量复用真机接口：

```text
Nav2/MoveIt 2
    ↓ ROS 2 command interface
controller_manager
    ↓
仿真 hardware interface
    ↓
Gazebo joint/plugin
    ↓
模拟关节状态、编码器和 odom
```

验证控制闭环时应逐层观察：

```bash
ros2 control list_controllers
ros2 control list_hardware_interfaces
ros2 topic echo /joint_states --once
ros2 topic echo /odom --once
ros2 topic echo /cmd_vel --once
```

仿真中常见“机器人不动”原因：

- 控制器没有加载或没有进入 `active`。
- joint 名称与 URDF/SDF 或控制器配置不一致。
- 命令接口和状态接口类型不匹配。
- 轮子 joint 轴方向或旋转限制错误。
- 仿真时间没有推进。
- 物理引擎中机器人被地面穿透、悬空或摩擦参数异常。

### 12.10 物理稳定性与仿真步长

物理仿真不是越快越好。需要平衡仿真步长、控制周期、传感器周期和计算资源：

```text
物理步长足够小
  → 控制器按稳定周期读取/写入
  → 传感器按独立频率发布
  → ROS 2 算法消费带时间戳的数据
```

若物理步长过大，可能出现穿模、接触弹跳和控制不稳定；若步长过小，仿真速度下降，控制器可能无法实时运行。调试时先固定步长和更新率，再改变物理材质或控制参数，避免变量同时变化。

仿真稳定性检查：

- 机器人静止时不会持续抖动或下沉。
- 轮子接触地面但不会穿透。
- 关节位置、速度和力矩没有非物理尖峰。
- 关闭控制命令后机器人按预期减速或停止。
- 传感器时间戳与仿真时间单调一致。

### 12.11 Sim-to-Real 的差异分类

仿真到真机的差异可以分成四类：

| 差异 | 示例 | 处理方法 |
|---|---|---|
| 几何差异 | 尺寸、安装外参、工具和 footprint | 实测建模、标定、版本管理 |
| 动力学差异 | 摩擦、质量、阻尼、柔性和负载 | 参数测量、范围随机化、真机辨识 |
| 感知差异 | 噪声、延迟、遮挡、曝光和反射 | 传感器模型、数据回放、鲁棒算法 |
| 系统差异 | 网络、CPU、驱动、时钟和安全回路 | 接口一致、性能测试、故障注入 |

迁移时不要只比较最终成功率，还要比较中间信号：速度跟踪、odom 漂移、激光数据质量、控制延迟、路径误差、最小障碍距离和恢复行为。

### 12.12 参数随机化与鲁棒性测试

为了避免算法只适应单一仿真参数，可以在合理范围内随机化：

- 轮径、轮距、质量和质心。
- 摩擦、阻尼、轮滑和控制延迟。
- 传感器噪声、频率、丢帧和外参小偏差。
- 障碍物位置、目标位置和动态障碍速度。
- 初始位姿、地图误差和电池/执行器能力。

随机化必须有边界和记录。不能把不符合真实设备的极端参数当作鲁棒性证明，也不能在结果失败后只保留成功样本。建议保存随机种子和每次测试的参数，保证失败场景可以重放。

### 12.13 仿真回归测试矩阵

建议建立固定测试矩阵：

| 类别 | 场景 | 主要指标 |
|---|---|---|
| 模型 | 空载静止、关节运动、碰撞检查 | TF、姿态、碰撞和稳定性 |
| 控制 | 直行、旋转、变速、停止 | 速度误差、超调、停止距离 |
| 传感器 | 噪声、延迟、遮挡、断线 | 频率、延迟、健康状态和降级 |
| 定位 | 起点误差、回环、地图变化 | 收敛时间、位姿误差和跳变 |
| 导航 | 窄门、动态障碍、不可达目标 | 成功率、路径长度、最小间距 |
| 故障 | 控制器退出、网络断开、时间暂停 | 安全停止、恢复和日志完整性 |
| 性能 | 不同分辨率和障碍数量 | CPU、内存、实时性和仿真速度 |

回归测试的关键不是场景数量，而是每个场景都有固定输入、明确预期和可比较输出。修改 URDF、控制器、传感器参数或 Nav2 配置后，应重新执行受影响的测试。

### 12.14 仿真调试顺序

推荐使用以下顺序，不要从 Nav2 直接开始：

1. 验证 Xacro 展开和 `check_urdf`。
2. 在 RViz2 中验证 RobotModel 和 TF。
3. 在 Gazebo 中验证静止、重力、碰撞和关节运动。
4. 验证 `/clock`、`use_sim_time` 和传感器 Topic。
5. 验证 `ros2_control` 控制器和关节反馈。
6. 验证 odom、激光、IMU 和传感器外参。
7. 接入 SLAM/定位和地图。
8. 接入 Nav2/MoveIt 2，先做近距离简单任务。
9. 加入噪声、延迟、动态障碍和故障注入。
10. 与真机按相同指标比较并记录差异。

### 12.15 第十二章学习验收

完成本章后，至少应能够：

- 解释 URDF/Xacro、SDF、Gazebo、物理引擎、插件、Bridge 和 ROS 2 算法的职责边界。
- 创建一个包含世界、机器人、地面、障碍物和传感器的可重复仿真场景。
- 检查 `/clock`、`use_sim_time`、传感器时间戳和 TF 的一致性。
- 使用 `ros_gz_bridge` 或 ROS 2 插件验证激光、IMU、相机和控制命令链路。
- 使用 `ros2_control` 检查仿真硬件接口、控制器状态和 joint feedback。
- 解释物理步长、控制周期、传感器周期和计算资源之间的关系。
- 为仿真加入噪声、延迟、丢帧、遮挡和参数随机化。
- 建立模型、控制、传感器、定位、导航和故障回归测试矩阵。
- 通过相同的 Topic、TF、指标和安全策略比较仿真与真机。

第十二章的交付物应包括：一个可重复启动的仿真 world、一份仿真控制器配置、一张 Gazebo/ROS 2 数据链路图、一组 Sim-to-Real 差异记录，以及一份包含正常、噪声和故障场景的回归测试报告。

## 13. RViz2、Foxglove 与 rosbag2

### 13.1 RViz2：在线空间调试

RViz2 适合快速检查：

- TF 树和坐标方向。
- RobotModel 与 URDF 是否重合。
- LaserScan、PointCloud2、Image 和地图。
- 全局路径、局部轨迹、目标点和代价地图。
- Marker、Polygon、轨迹和诊断标记。

建议固定一个导航调试布局：左侧 3D 视图，中间地图和路径，右侧 TF/状态/参数面板。每次只改变一个显示项，避免把“显示问题”误判为“算法问题”。

### 13.2 Foxglove：离线分析与多数据联合

Foxglove 更适合查看 rosbag2/MCAP、Plot 曲线、Raw Messages、Diagnostics，以及保存团队共享的 Layout。典型用途是同时分析 `/cmd_vel`、`/odom`、`/scan`、局部路径、目标距离和控制器状态。

### 13.3 rosbag2 记录原则

记录前先列出问题假设，再选择最小必要 Topic：

```bash
ros2 bag record -o nav_debug \
  /tf /tf_static /odom /scan /cmd_vel \
  /plan /local_plan /local_costmap/costmap \
  /diagnostics /clock
```

记录后保存：

- ROS 2 发行版和软件提交号。
- 参数 YAML 和地图文件校验值。
- 机器人硬件配置、传感器安装和电池状态。
- 复现步骤、目标点、环境和预期行为。

没有这些上下文，bag 往往只能“看到现象”，不能复现原因。

### 13.4 RViz2 的显示层次

RViz2 中看到的内容可以按四层理解：

```text
Fixed Frame
  ↓
TF 变换
  ↓
消息数据和 frame_id
  ↓
Display 插件渲染
```

因此“显示不出来”不一定是 RViz2 的问题，可能来自固定坐标系不存在、消息 frame 无法变换、Topic 没有数据或 QoS 不匹配。

常用 Display 与排查重点：

| Display | 主要用途 | 首要检查 |
|---|---|---|
| Grid | 空间方向和尺度参考 | `Fixed Frame`、网格大小 |
| TF | 坐标树和 frame 方向 | TF 连通性、更新时间 |
| RobotModel | URDF 和关节状态 | `robot_description`、joint states |
| LaserScan | 2D 激光和外参 | Topic、frame、量程和时间 |
| PointCloud2 | 三维点云 | 字段、密度、颜色和带宽 |
| Image/Camera | 图像和相机视锥 | 图像 Topic、内参和 frame |
| Map | 静态地图 | 地图 Topic、原点和分辨率 |
| Path | 全局/局部路径 | 路径 frame、时间和轨迹内容 |
| Marker | 算法调试几何 | namespace、ID、生命周期 |
| Odometry/Pose | 轨迹和状态 | frame、协方差和时间 |

建议先添加 Grid、TF 和 RobotModel，再逐个添加传感器和算法输出。一次添加太多 Display 会让 CPU、网络和视觉注意力都超载。

### 13.5 RViz2 标准调试布局

#### TF/模型布局

适合排查 URDF、静态 TF 和传感器外参：

```text
3D View：Grid + TF + RobotModel + Axes
左侧：Displays、Fixed Frame、Topic 和 Status
右侧：选中 link、sensor frame 和姿态信息
```

#### 导航布局

建议同时显示：

- Map、Global Costmap、Local Costmap。
- RobotModel、TF、Footprint。
- Global Plan、Local Plan/MPPI Trajectory。
- LaserScan、目标 Pose 和当前 odom。

#### 机械臂布局

建议显示：

- RobotModel、关节状态和末端 Axes。
- Planning Scene、碰撞物体和目标 Pose。
- 轨迹、末端路径和工具 TCP。

布局文件应与代码和参数一起版本管理。一个好的布局可以让团队成员在同一视觉上下文中复现问题。

### 13.6 RViz2 工具与交互语义

常用工具的输入 frame 必须明确：

| 工具 | 用途 | 常见误区 |
|---|---|---|
| `2D Pose Estimate` | 设置定位初始位姿 | 地图 frame、箭头方向或 QoS 错误 |
| `2D Nav Goal` | 发送导航目标 | 目标角度、Action Server 或 lifecycle 未就绪 |
| `Publish Point` | 发布地图中的点 | 订阅者等待的 Topic 不一致 |
| `Interact` | 选择和操作对象 | 误把鼠标交互当作控制命令 |
| `Select` | 查看 Marker、link 或对象 | 没有选择到正确 Display |

使用工具后要观察对应消息是否真的发布：

```bash
ros2 topic echo /initialpose --once
ros2 topic echo /goal_pose --once
ros2 action info /navigate_to_pose
```

### 13.7 Foxglove 的实时连接与离线分析

Foxglove 的优势是把多个 Topic 放在同一时间轴和布局中进行分析。实时调试可以观察当前系统，离线模式则更适合精确复现和比较。

常用面板组合：

| 面板 | 适合问题 |
|---|---|
| 3D | TF、模型、点云、激光、路径和障碍 |
| Image | 视觉输入、曝光、遮挡和检测结果 |
| Plot | 速度、误差、延迟、温度和协方差 |
| Raw Messages | 字段、时间戳、frame 和参数语义 |
| State Transitions | 生命周期、行为树和任务状态 |
| Diagnostics | 设备健康、频率、超时和错误码 |
| Teleop/Publish | 受控调试输入，必须配合安全限制 |

实时连接时先确认网络、ROS 2 Domain、bridge 和 Topic 权限；离线分析时先确认 bag 格式、时间源和自定义消息定义。

### 13.8 rosbag2 记录策略

记录 Topic 前先写出问题假设：

```text
假设：导航控制器在传感器延迟升高时输出停止命令
需要：scan、cmd_vel、odom、costmap、diagnostics、clock、tf
```

再选择必要 Topic：

```bash
ros2 bag record -o nav_debug \
  /tf /tf_static /odom /scan /cmd_vel \
  /plan /local_plan /local_costmap/costmap \
  /diagnostics /clock
```

记录策略：

- 先记录小范围、短时间、可复现的问题，不要默认录下所有 Topic。
- 高带宽图像和点云需要考虑磁盘、写入速度和存储周期。
- 记录 `/tf` 与 `/tf_static`，否则离线显示经常无法还原空间关系。
- 记录 `/clock` 用于仿真或回放时间一致性。
- 记录输入、输出和诊断，不要只记录最终结果。
- 记录开始和结束时的场景、目标、版本、参数和人工操作。

查看 bag 元数据：

```bash
ros2 bag info nav_debug
```

### 13.9 rosbag2 回放、时钟与复现

离线回放的关键是让算法节点使用 bag 的时间：

```bash
ros2 bag play nav_debug --clock
```

回放前检查：

1. 算法节点和可视化工具是否启用 `use_sim_time`。
2. bag 是否包含 `/clock`、`/tf`、`/tf_static` 和需要的输入 Topic。
3. 自定义消息类型和依赖是否安装。
4. 回放时是否需要关闭原始驱动，避免实时数据与 bag 数据混在一起。
5. 是否需要降低播放速率，以便算法和可视化跟上。

实时驱动和 bag 同时发布同一 Topic，会造成“看起来数据存在但内容不稳定”。复现环境应明确数据源只有一个，并记录命令和参数。

### 13.10 多信号时间线分析

机器人故障通常不是一个 Topic 单独异常，而是多个信号之间的时间关系发生变化。建议按同一时间轴对齐：

```text
传感器时间戳
  → TF 可查询时间
  → 定位输出
  → 规划路径
  → cmd_vel
  → 实际 odom
  → 诊断和状态变化
```

例如分析“障碍前没有停车”：

1. 找到障碍首次出现在 `/scan` 或点云的时间。
2. 检查局部 costmap 何时出现障碍。
3. 检查控制器何时降低速度或发布零速度。
4. 比较 odom 和实际停止位置。
5. 关联传感器延迟、TF 查询失败和诊断告警。

只看 `/cmd_vel` 无法判断是感知慢、costmap 没更新、控制器拒绝轨迹，还是底盘没有执行。

### 13.11 常见可视化问题

| 现象 | 优先检查 |
|---|---|
| RViz2 Global Status 红色 | Fixed Frame、TF、Topic 和插件状态 |
| Display 显示 `No transform` | `frame_id`、TF 连通、时间戳和缓存 |
| RobotModel 不显示 | `robot_description`、URDF、mesh 路径和尺度 |
| LaserScan 不显示 | Topic 类型、QoS、量程、frame 和时间 |
| PointCloud2 很卡 | 点数、降采样、渲染风格、网络和 GPU |
| Map 不显示 | 地图 Topic、map frame、QoS 和时间 |
| 2D Nav Goal 无反应 | Action Server、lifecycle、目标 frame 和 BT |
| Foxglove 没有曲线 | 字段路径、数值类型、时间轴和消息是否变化 |
| bag 打开后自定义消息乱码 | 消息包、Schema、bag 格式和版本 |
| 回放后 TF 全部错误 | `/clock`、`use_sim_time`、`/tf_static` 缺失 |

### 13.12 常见录包问题

#### 录不到数据

检查 Topic 是否存在、QoS 是否匹配、记录命令是否在正确的 ROS 2 环境中执行，以及磁盘是否可写。

#### bag 很大但没有帮助

通常是录了大量无关图像或点云，却没有录输入输出、TF、时间和诊断。应根据故障假设缩小 Topic 集合。

#### 回放速度不稳定

检查磁盘吞吐、解压、CPU、网络和可视化渲染。不要把播放速度异常误判为算法实时性问题。

#### 回放结果与现场不同

检查参数文件、地图、模型、TF 静态变换、自定义消息、环境变量和仿真时间是否一致。

### 13.13 调试布局和数据资产管理

建议按项目管理以下资产：

```text
debug_assets/
├── rviz/
│   ├── navigation.rviz
│   └── manipulator.rviz
├── foxglove/
│   ├── navigation_layout.json
│   └── sensor_layout.json
├── bags/
│   └── README.md
├── plots/
├── screenshots/
└── reports/
```

每个 bag 或布局都应记录：

- 生成日期和机器人名称。
- 软件提交号、参数和地图版本。
- 数据来源是仿真、真机还是回放。
- 是否包含 `/clock`、TF 和自定义消息。
- 数据保留期限、隐私和磁盘大小。
- 结论、已知限制和下一步。

不要只提交一张截图作为故障结论。截图适合说明现象，bag、参数和日志才支持复现。

### 13.14 一个完整的导航故障复现流程

以“机器人导航时在障碍前没有及时停止”为例：

1. 记录问题假设、场景、目标点和预期停止距离。
2. 录制 `/scan`、`/tf`、`/tf_static`、`/odom`、`/cmd_vel`、costmap、diagnostics 和 `/clock`。
3. 用 RViz2 实时确认障碍是否可见、footprint 是否正确。
4. 用 Foxglove 画出传感器到控制命令的时间线。
5. 用 `ros2 bag play --clock` 在干净环境回放。
6. 分别替换传感器、costmap、控制器参数，保持其他条件不变。
7. 记录延迟、停止距离、控制输出和恢复行为。
8. 修复后用原始 bag 和新的现场数据进行回归验证。

### 13.15 第十三章学习验收

完成本章后，至少应能够：

- 根据问题选择 RViz2、Foxglove 或 rosbag2，而不是只使用一种工具。
- 使用 RViz2 的 Fixed Frame、TF、RobotModel、传感器、路径和代价地图完成在线排查。
- 建立导航和机械臂专用的可复用 RViz2/Foxglove 布局。
- 根据问题假设选择最小必要 Topic，记录 `/tf`、`/tf_static`、输入、输出和诊断。
- 使用 `ros2 bag info`、`ros2 bag play --clock` 完成离线复现。
- 在同一时间轴上关联传感器、TF、定位、规划、控制和实际运动。
- 识别可视化错误、数据错误、时间错误和算法错误的区别。
- 管理 bag、参数、地图、布局、截图和报告等调试资产。
- 完成一次从现场现象到离线复现、参数对比和回归验证的完整流程。

第十三章的交付物应包括：一份标准 RViz2 调试布局、一份 Foxglove 分析布局、一份最小 Topic 录制清单、一个可回放 bag，以及一份包含时间线、根因、修复和回归结果的故障报告。

## 14. 一个可维护的机器人软件架构

本章关注的是：当机器人从“能跑”走向“可长期维护”时，如何把硬件、驱动、感知、定位、规划、控制、任务和调试能力拆成边界清晰、可验证、可回滚的模块。好的架构不是把目录分得更多，而是让每一层都能独立理解、独立替换、独立排错。

### 14.1 为什么机器人项目容易失控

机器人系统容易失控，通常不是因为某个算法“写错了”，而是因为多个职责被挤进了同一条代码路径：

- 驱动、算法、任务逻辑和调试代码混在同一个节点里。
- 配置、地图、标定和业务参数散落在不同目录和不同仓库。
- 真机、仿真和离线回放共用一套启动方式，导致场景切换成本很高。
- 数据流没有明确定义，出了问题以后只能靠猜。
- 能跑通的实验没有被记录成版本化交付物，过几天就复现不出来。

这类问题的共同结果是：一处修改引发多处联动，局部修复会破坏别的场景，最终系统越来越依赖“经验记忆”而不是“明确契约”。

### 14.2 一个可维护架构要回答的问题

在动手拆分之前，先把下面这些问题回答清楚：

| 问题 | 需要先回答什么 |
|---|---|
| 这层负责什么 | 它的输入、输出和失败语义是什么？ |
| 谁依赖它 | 上层可以调用哪些接口，下层不能被谁反向依赖？ |
| 怎么启动 | 真机、仿真和测试是否使用同一套入口？ |
| 怎么替换 | 硬件、算法和参数是否能在不改业务代码的情况下切换？ |
| 怎么验证 | 这层最小的测试输入、预期输出和健康检查是什么？ |
| 出错怎么办 | 失败后是重试、降级、停止，还是切到安全状态？ |

如果这些问题没有答案，后面的包拆分、launch 拆分和测试拆分都会变成“看起来整齐，实际上仍然耦合”。

### 14.3 推荐的分层视图

可以把机器人软件理解为从下到上的六层：

```text
设备层      → 电机、编码器、激光、相机、IMU、总线
驱动层      → 设备适配、协议转换、原始数据发布
状态层      → 里程计、TF、滤波、标定、时间同步
能力层      → 感知、定位、建图、规划、控制
安全层      → 限速、急停、看门狗、权限、故障降级
任务层      → 导航、抓取、对接、巡检、业务编排
```

推荐的数据方向是：

- 运动命令自上而下传递，且必须经过安全门。
- 状态、诊断和日志自下而上回传，且尽量标准化。
- 跨层调用优先使用 Topic、Action、Service、TF 和参数契约，而不是直接访问内部对象。

在这个视图里，`hardware`、`localization`、`navigation`、`bringup` 和 `application` 不是随意起名，而是把职责拆到对应的层。后面的包结构就是按这个思路组织的。

推荐按职责拆分，而不是按“节点数量”拆分：

```text
robot_description/
├── urdf/
├── meshes/
├── rviz/
└── config/

robot_hardware/
├── base_driver/
├── sensor_drivers/
└── ros2_control_plugins/

robot_localization/
├── odometry/
├── ekf/
├── slam_or_amcl/
└── map_server/

robot_navigation/
├── nav2_params.yaml
├── behavior_trees/
├── maps/
└── launch/

robot_bringup/
├── launch/
├── config/
└── scripts/

robot_application/
├── task_manager/
├── behavior_tree/
├── docking/
└── diagnostics/
```

每个包都应有明确的 README、参数说明、启动方式、依赖和验收方法。应用层不能直接绕过底盘控制器写电机命令；安全层不能依赖一个可能被应用层阻塞的普通回调。

### 14.4 软件架构的基本原则

一个可维护的机器人系统应同时满足以下原则：

1. **职责单一**：一个包或节点主要解决一个问题，不把驱动、算法、任务和安全逻辑混成巨型节点。
2. **接口稳定**：上层依赖消息、Action、参数和 TF 契约，而不是依赖下层类的内部实现。
3. **依赖单向**：应用层可以调用导航和控制能力，但底层驱动不应反向依赖具体业务任务。
4. **故障隔离**：传感器、算法和任务进程可以独立重启，故障不会无限扩散。
5. **配置外置**：地图、标定、速度限制和算法参数不硬编码在业务逻辑中。
6. **可观测**：每个关键模块都能通过状态、诊断、日志和数据记录解释自己的行为。
7. **可替换**：仿真硬件可以替换真机硬件，DWB/MPPI 等插件可以在同一接口下替换。
8. **可验证**：每个模块都有最小启动方式、测试输入、预期输出和失败处理。

不要把“节点数量越多”误认为模块化。模块边界应该由职责、数据流、故障边界、实时性和部署需要共同决定。

### 14.5 包、节点与组件的边界

包是代码、资源、接口和依赖的发布单元；节点是运行时职责单元；组件是可以被加载到进程中的节点实现。三者并不等价：

| 对象 | 主要问题 | 示例 |
|---|---|---|
| 包 | 如何构建、安装、发布和复用？ | `robot_description` |
| 节点 | 运行时谁负责什么？ | `lidar_driver`、`ekf_filter` |
| 组件 | 是否需要进程内组合？ | 高带宽图像处理组件 |
| Launch | 如何按场景编排节点？ | 仿真 bringup、真机 bringup |
| 配置 | 不同机器人/环境使用哪些参数？ | `nav2_params.yaml` |

拆分包时可以使用以下判断：

- 是否有独立的输入、输出和版本周期？
- 是否需要独立测试、部署或重启？
- 是否会被多个机器人或项目复用？
- 是否包含不同语言、硬件或第三方依赖？
- 故障发生时是否应该与其他功能隔离？

例如 `robot_description` 不应依赖 Nav2；`base_driver` 不应依赖具体任务名称；`robot_application` 可以依赖导航 Action，但不应直接操作电机寄存器。

### 14.6 接口契约与数据流设计

接口契约应写明输入、输出、坐标、时间、频率、QoS、参数和错误语义：

| 接口项 | 示例 |
|---|---|
| 名称与类型 | `/scan`：`sensor_msgs/msg/LaserScan` |
| 发布者/订阅者 | `lidar_driver` → `slam_toolbox`、Nav2 costmap |
| `frame_id` | `laser_link` |
| 时间语义 | 传感器采集时间，允许延迟范围 |
| 频率 | 目标频率、最大间隔和超时阈值 |
| QoS | reliability、durability、depth |
| 单位 | 米、弧度、米每秒、秒 |
| 无效数据 | NaN、Inf、空帧、超时如何处理 |
| 故障语义 | 降速、停车、重试、人工接管 |

建议为公共接口建立表格，而不是把约定只写在开发者记忆中。接口变更时，要同时更新消息、参数、launch、测试、README 和迁移说明。

### 14.7 Bringup 与 Launch 分层

推荐使用“基础层 → 功能层 → 应用层”的启动结构：

```text
base_bringup.launch.py
├── robot_description
├── robot_state_publisher
├── hardware/simulation interface
└── static TF

perception_bringup.launch.py
├── camera
├── lidar
├── imu
└── diagnostics

localization_bringup.launch.py
├── odometry
├── EKF
├── SLAM/AMCL
└── map server

navigation_bringup.launch.py
├── costmap
├── planner/controller
├── behavior tree
└── lifecycle manager

application_bringup.launch.py
├── task manager
├── docking
├── fleet/mission interface
└── operator UI
```

每个 launch 都应支持必要的 Launch Arguments，例如：

- `use_sim_time`。
- `use_fake_hardware` 或 `simulation`。
- `namespace` 和机器人名称。
- 地图路径、参数文件和 RViz 配置。
- 是否启动可视化、录包和调试日志。

不要把真机设备驱动和 Gazebo 插件无条件同时启动，也不要在多个 launch 中重复启动同一条 TF 或同一个控制器。

### 14.8 配置、参数与环境隔离

建议把配置按稳定性和环境拆开：

```text
config/
├── common/
│   ├── frames.yaml
│   └── diagnostics.yaml
├── hardware/
│   ├── real_base.yaml
│   └── simulation_base.yaml
├── localization/
│   ├── ekf.yaml
│   └── amcl.yaml
├── navigation/
│   └── nav2_params.yaml
└── robots/
    ├── robot_a.yaml
    └── robot_b.yaml
```

配置管理原则：

- 公共默认值、硬件差异和场景差异分开。
- 真机安全限制不能被调试参数无意覆盖。
- 每次实验记录参数文件、地图、模型和代码提交号。
- 参数变更应有范围检查、单位说明和版本记录。
- 密钥、网络凭据和隐私数据不能硬编码到仓库。
- 不要使用大量隐含环境变量改变运行行为，关键配置应在启动日志中打印。

### 14.9 生命周期、状态机与启动健康检查

机器人应用不应只依赖“进程还活着”判断系统健康。建议为关键组件定义状态：

```text
STARTING
  ↓
SELF_CHECK
  ↓
READY
  ↓
RUNNING ↔ PAUSED
  ↓
DEGRADED
  ↓
ERROR / E_STOP
```

启动健康检查可以包括：

- ROS 2 发行版和配置版本。
- 传感器 Topic 是否存在、频率是否正常。
- `map -> odom -> base_link` 是否连通。
- 控制器是否 active，命令是否超时。
- 电池、电机、温度和急停状态。
- 地图、模型和标定文件是否存在且校验值正确。
- 关键节点是否进入预期 lifecycle 状态。

健康检查失败时，系统应明确禁止哪些动作。例如定位不可用时可以禁止导航；急停未复位时应禁止所有运动；激光失联时应禁止需要实时避障的任务。

### 14.10 错误处理与故障边界

每个模块都应区分可恢复错误、不可恢复错误和安全错误：

| 类型 | 示例 | 处理方式 |
|---|---|---|
| 可恢复 | 单次传感器丢帧、短时网络抖动 | 重试、降频、等待恢复并记录 |
| 功能失败 | 规划无路径、IK 无解、抓取失败 | 取消任务、换策略或请求人工处理 |
| 系统错误 | 节点崩溃、控制器失活、磁盘满 | 重启、切换备用、停止相关功能 |
| 安全错误 | 急停、碰撞、超速、通信超时 | 立即进入安全状态，禁止自动恢复运动 |

错误处理不能只返回一个布尔值。建议包含错误码、时间、模块、上下文、重试次数、当前状态和建议动作。自动重试必须有限次，并且不能绕过安全门。

### 14.11 测试金字塔

机器人软件需要从快到慢建立多层测试：

```text
单元测试
  → 接口和消息测试
  → 节点集成测试
  → Launch/系统测试
  → 仿真场景回归
  → 硬件在环测试
  → 真机验收测试
```

各层适合验证：

| 测试层 | 典型内容 |
|---|---|
| 单元 | 坐标变换、运动学、参数解析、状态转移 |
| 接口 | 消息类型、单位、frame、QoS 和错误码 |
| 集成 | 多节点通信、TF 树、控制器和 launch |
| 仿真 | 导航、抓取、传感器失联、动态障碍 |
| 硬件在环 | 驱动、通信延迟、编码器和电机反馈 |
| 真机 | 低速、急停、故障恢复和任务成功率 |

不要把所有问题都留到真机阶段。越早发现模型、接口、参数和状态机错误，修复成本越低。

### 14.12 日志、诊断与可观测性

架构设计时就要预留可观测性：

- 每个节点输出启动版本、参数来源和关键接口。
- 每个硬件驱动输出设备状态、错误码和重连次数。
- 每个算法输出输入新鲜度、计算耗时、成功率和拒绝次数。
- 每个任务输出任务 ID、目标、状态转移和结果。
- 每个安全事件输出急停、限速、超时和人工接管原因。

建议把运行信息分成三类：

```text
日志：解释发生了什么
诊断：说明当前是否健康
指标：描述一段时间内表现如何
```

例如“导航失败”是日志事件，“local costmap sensor timeout”是诊断状态，“过去 100 次任务成功 96 次”是指标。三者不能互相替代。

### 14.13 部署、升级与回滚

机器人部署应把代码、配置、模型、地图、容器/依赖和固件视为一个版本化交付物：

```text
release/
├── software_commit.txt
├── ros_distro.txt
├── params/
├── maps/
├── robot_description/
├── firmware_versions.txt
├── startup_commands.txt
└── rollback.md
```

升级前确认：

- 是否有当前版本备份和回滚包。
- 是否能在仿真或备用设备上完成冒烟测试。
- 地图、标定、参数和固件是否兼容。
- 升级失败时机器人如何进入安全状态。
- 现场是否保留人工接管和恢复介质。

不要把“重新安装依赖”和“升级生产机器人”当成同一类操作。生产部署必须可重复、可审计、可回滚。

### 14.14 CI/CD 与质量门禁

机器人项目的 CI 可以逐步加入以下门禁：

```text
格式/静态检查
  → 单元测试
  → colcon 干净构建
  → launch 冒烟测试
  → URDF/Xacro 检查
  → 接口和参数检查
  → 仿真回归场景
  → 生成测试报告和构建产物
```

每次提交至少应该检查：

- 包依赖是否完整。
- C++/Python 是否能在干净工作空间构建。
- launch、YAML、URDF 和资源是否正确安装。
- 消息、Topic、Action、参数和 TF 契约是否发生破坏性变化。
- 关键仿真场景成功率和性能是否退化。

真机测试不一定每次自动执行，但应有明确的手动验收步骤和结果记录。

### 14.15 一个可落地的机器人软件数据流

```text
hardware/
  → driver/
  → normalized sensor topics
  → state estimation
  → planning/navigation
  → controller
  → safety gate
  → hardware command

diagnostics ← 每一层的健康状态、延迟、错误码
rosbag2    ← 关键输入、输出、TF、时钟和诊断
task layer → Action、状态机、任务日志和人工接口
```

这里的关键是“标准化输入”和“安全出口”：驱动层将不同设备转换为统一 ROS 2 消息；所有运动命令在到达硬件前经过限速、超时、急停和权限检查。

### 14.16 第十四章学习验收

完成本章后，至少应能够：

- 按职责拆分 robot description、hardware、localization、navigation、bringup 和 application 包。
- 为 Topic、Action、TF、参数和诊断建立接口契约。
- 设计基础层、功能层和应用层 launch，并区分仿真与真机入口。
- 管理地图、标定、模型、参数、固件和代码版本。
- 设计 lifecycle、健康检查、状态机、错误码和故障降级。
- 建立从单元测试到仿真、硬件在环和真机验收的测试金字塔。
- 通过日志、诊断、指标和 rosbag2 让系统可观测、可复现。
- 设计部署、升级、回滚和 CI 质量门禁。
- 解释为什么应用层不能绕过控制器和安全门直接操作硬件。

第十四章的交付物应包括：一张系统分层架构图、一份包与节点职责表、一份公共接口契约、一套分层 launch、一份配置/版本管理方案，以及一份包含测试、部署、回滚和故障处理的工程说明。

## 15. 分层排错手册

第十五章不是“故障清单”，而是一个固定顺序的排错方法：先定位现象属于哪一层，再用最小证据链确认输入、输出、时序和约束，最后才动参数或改代码。越是看起来复杂的问题，越要先回到最底层事实。

### 15.0 排错总原则

排错时建议遵循以下顺序：

1. **先复现**：确认问题可稳定触发，记录触发条件、频率和持续时间。
2. **先证据**：先看 Topic、TF、日志、bag、参数和版本，不先靠猜测改算法。
3. **先下后上**：先查硬件、驱动、时间和坐标，再查规划、行为树和任务逻辑。
4. **先最小化**：关闭不必要节点，只保留最小闭环，避免把问题藏进复杂系统。
5. **先对比**：拿正常场景、历史 bag 或同类机器人做对照。
6. **先记录**：每次改动都要记下命令、参数、版本和现象变化，避免反复试错后失去线索。

一个实用判断是：如果现象能够被 `ros2 topic echo`、`ros2 topic hz`、`tf2_echo`、`rqt_graph`、`rviz2` 或 `rosbag2` 直接验证，就先用这些工具把事实固定下来，再进入代码层。

### 15.1 机器人完全不动

```text
节点是否启动
  → /cmd_vel 是否发布
  → 底盘是否订阅
  → 控制器是否 active
  → 急停/看门狗是否触发
  → 电机是否使能
  → 编码器是否变化
  → odom 是否反馈
```

如果机器人完全不动，优先把问题分成三类：

- **命令没到**：`/cmd_vel` 没有发布，或者发布在错误命名空间。
- **命令没被接受**：底盘没有订阅、QoS 不匹配、控制器没 active。
- **命令没被执行**：急停、权限、限速、故障状态或驱动异常拦截了输出。

在这类问题里，不要先调路径规划参数；先确认底盘链路本身是否闭合。

### 15.2 RViz2 不显示机器人或激光

1. 检查 `Fixed Frame` 是否存在。
2. 检查 `robot_description` 是否发布且 XML 可解析。
3. 检查 `frame_id` 拼写和 TF 可查询性。
4. 检查 Topic 类型和 QoS。
5. 检查数据是否在视野外或时间戳异常。

如果 RViz2 中“看不见”，常见原因其实只有四类：没有数据、坐标系错了、时间不对、显示配置错了。优先看 `tf2_echo`、`ros2 topic echo` 和消息时间戳，而不是先怀疑 RViz2 本身。

### 15.3 Nav2 无法启动

1. 查看 lifecycle 节点状态。
2. 检查地图、参数和插件类型是否匹配当前发行版。
3. 检查 `map -> odom -> base_link` 是否完整。
4. 检查 costmap 的传感器 source、frame 和 observation source。
5. 检查控制器是否能发布合法速度。

Nav2 启动失败通常不是单一参数错误，而是接口契约没有同时满足。常见触发点包括：

- 地图文件、参数文件或插件名与当前发行版不兼容。
- `use_sim_time`、TF 和消息时间不同步。
- lifecycle 节点没有全部进入 `active`。
- costmap 的传感器数据没有正确进入目标 frame。
- 控制器输出被底盘限幅后变成无效命令。

### 15.4 导航绕圈、撞障碍或穿墙

优先检查底层事实：

- 机器人 footprint 是否真实。
- 激光是否安装方向正确。
- 地图分辨率和原点是否正确。
- 局部 costmap 是否实时更新。
- 里程计是否连续且尺度正确。
- 控制器的速度/加速度限制是否超过底盘能力。
- 目标容差是否过小，导致机器人在噪声中持续修正。

如果问题表现为“走得动但不对”，优先把它归为坐标、尺度、约束或代价地图问题，而不是先调大规划器搜索范围。大多数绕圈和穿墙，本质上都是输入不可信。

### 15.5 SLAM 地图重影或漂移

检查顺序：

```text
激光数据 → 激光 frame 外参 → odom 连续性
        → 时间同步 → 运动速度
        → 环境可观测性 → 回环参数
```

不要先盲目增大回环权重；如果传感器、TF 或时间不可信，优化器只会把错误数据拟合得更复杂。

### 15.6 传感器有数据但上层不认

有时 Topic 明明在发布，但 RViz2、定位、建图或导航仍然“看不到”。这类问题通常出在接口契约不一致：

- `frame_id` 错误，数据落在了错误坐标系。
- 时间戳过旧、未来时间或跳变，导致消息被丢弃。
- QoS 不匹配，订阅端和发布端没有真正建立连接。
- 消息类型对了，但单位、方向或顺序不对。
- 数据范围异常，例如距离全零、全满、NaN 或空帧。

排查顺序建议是：先看消息是否真实发布，再看时间戳，再看 `frame_id`，最后看上层算法是否接受该数据。

### 15.7 TF 树连通但坐标不对

TF 能查到不等于 TF 正确。以下情况最容易误导排查：

- 父子 frame 名称写对了，但轴方向反了。
- 静态外参写对了格式，但安装方向和实物方向不一致。
- `map -> odom` 和 `odom -> base_link` 都存在，但语义被混用了。
- 变换发布频率太低或时间戳不同步，查询时落到旧数据。

建议用“已知距离、已知姿态、已知运动”三种方式验证 TF：先拿尺量检查固定安装，再让机器人原地转圈看旋转方向，最后用短距离直线运动验证里程计尺度。

### 15.8 底盘执行和控制器异常

如果上层已经发出合法命令，但机器人仍然不按预期运动，重点看控制链路：

1. 检查控制器是否处于 `active`。
2. 检查 `/cmd_vel` 是否被底盘订阅并按频率刷新。
3. 检查限速、加速度限制和看门狗超时。
4. 检查电机使能、驱动告警和编码器反馈。
5. 检查是否存在急停、权限门禁或安全层阻断。

控制器问题常见的错误是“命令看起来正确，但执行端已经换了参考系或单位”。例如把线速度当成轮速，把角速度当成舵角，或者把米每秒和毫米每秒混用。

### 15.9 排错记录模板

建议每次故障都记录最少以下内容：

```text
现象描述：
触发条件：
影响范围：
系统版本：
ROS 2 发行版：
相关 Topic/TF：
相关参数：
日志片段：
rosbag 文件：
初步判断：
修复动作：
回归结果：
```

有了这份记录，后续排错才不只是“记得当时改过什么”，而是可以把故障转换成可复现、可对比、可回归的问题。

## 16. 安全与可靠性：从 Demo 到产品

### 16.1 风险来源

至少评估：

- 人员进入运动范围。
- 传感器遮挡、脏污、掉线或输出异常。
- 定位丢失、地图过期或坐标跳变。
- 控制器崩溃、CPU 过载、网络中断。
- 电机过流、过热、电池低电量。
- 软件升级、参数变更和地图切换。
- 急停后误恢复或任务状态不一致。

可以把这些风险归成三类：

- **输入风险**：传感器、时间、坐标、网络和地图本身不可信。
- **执行风险**：控制器、底盘、电机和安全链路没有按预期执行。
- **运维风险**：升级、切换、人工接管和恢复流程不受控。

做风险分析时，重点不是把风险名称写全，而是明确每个风险的触发条件、可检测信号、降级动作和恢复条件。

### 16.2 安全功能的边界

软件避障、软件限速和 ROS 2 节点中的停止逻辑不能自动等价于功能安全。需要根据实际设备和风险评估设计硬件急停、安全扫描器、限位、断能、独立看门狗和人工接管链路。机器人学习笔记可以解释工程方法，但不能替代适用的法规、标准、风险评估和专业安全认证。

### 16.3 故障处理状态机

```text
INIT → SELF_CHECK → IDLE → RUNNING → PAUSED
  │                    │       │         │
  └────── ERROR ←──────┴───────┴─────────┘
             ↓
          RECOVERY → IDLE
             ↓
          E_STOP
```

每个状态必须定义进入条件、退出条件、允许动作、禁止动作、超时策略和日志字段。建议把“暂停”“故障停止”“急停”分成不同语义：暂停可能允许恢复，故障停止需要诊断，急停需要明确复位。

### 16.4 可观测性

生产系统至少记录：

- 软件、参数、地图和模型版本。
- 任务 ID、目标点和状态转移。
- 节点生命周期和控制器状态。
- Topic 频率、延迟、丢包和 QoS。
- TF 查询失败和估计协方差。
- 电机、电池、温度、CPU、内存和磁盘。
- 关键故障前后的 rosbag2 片段。

### 16.5 安全状态与降级策略

安全系统的目标不是“永远不出错”，而是“出错时知道停在哪里、怎么停、谁能恢复”。建议把运行结果分成几种明确状态：

| 状态 | 含义 | 典型动作 |
|---|---|---|
| 正常运行 | 所有关键输入可信，任务可执行 | 允许导航、抓取、对接或巡检 |
| 受限运行 | 某些输入变差，但仍可继续 | 降速、缩小任务范围、降低自主性 |
| 暂停 | 需要人工确认或短时恢复 | 停止新任务，保留状态和上下文 |
| 故障停止 | 功能异常但不一定是安全事件 | 取消任务，记录诊断，等待处理 |
| 急停 | 出现人身或设备风险 | 立即切断运动输出并进入安全状态 |

常见降级动作包括：

- 降低最大速度和加速度。
- 禁止进入狭窄区域或复杂任务。
- 关闭高风险功能，仅保留回家或停靠。
- 切换到备用传感器、备用定位或备用控制通道。
- 触发人工接管并冻结任务状态。

降级策略要提前定义，不要等系统已经异常后才临时决定“还能不能继续跑”。

### 16.6 恢复、复位与人工接管

安全系统里最容易出问题的是“恢复”而不是“停止”。停止动作通常简单，复位和恢复却涉及状态一致性、现场确认和权限控制。

恢复前至少确认：

1. 风险源已经解除，例如障碍物已移走、传感器已恢复、急停已复位。
2. 系统状态已重新同步，例如 TF、定位、任务状态和控制器状态一致。
3. 当前任务是否仍然有效，还是应该重新规划或重新下发。
4. 人工接管是否已完成，并且恢复动作有明确授权。

建议把人工接管设计成显式流程，而不是“人可以随时改参数然后再试一次”。人工接管应留下日志、时间戳和操作结果，方便追溯。

### 16.7 上线前验证清单

机器人上线前，至少要确认以下项目：

- 急停是否真实有效，且复位后不会自动恢复运动。
- 失联、掉电、传感器拔除和定位丢失时是否进入预期状态。
- 控制器超时、看门狗和限速是否生效。
- 仿真、录包回放和真机在关键接口上是否保持一致。
- 任务失败时是否能回到安全位置或安全姿态。
- 升级、回滚和参数切换是否有明确操作步骤。
- 现场是否能快速查看日志、诊断和最近一次 bag。

如果这些项目没有通过，就不应把系统当作“可交付产品”，只能算“可演示原型”。

## 17. 推荐实践路线

第十七章把前面几章的知识串成一条学习路径。不要一上来就追求“完整机器人项目”，而是按阶段拿到可验证的小结果：先能通信，再能看见，再能动起来，再能定位，再能导航，最后再做工程化迁移。

建议每一阶段都保留三类产物：

- 一份最小可运行代码或配置。
- 一份验收记录，写清楚输入、输出和失败条件。
- 一份能复现问题的 bag、截图或日志片段。

如果某一阶段卡住，优先回退到前一阶段检查接口契约、坐标系、时间和版本，不要直接跳到更复杂的算法。

### 阶段一：ROS 2 通信

目标：能独立写 Publisher、Subscriber、Service、Action、参数和 launch。

练习：写一个节点发布速度命令，另一个节点模拟轮速并发布 odom；用 CLI 验证 Topic、频率和消息内容。

补充练习：

- 写一个参数节点，支持启动时覆盖默认值。
- 用 `ros2 topic list`、`ros2 topic echo`、`ros2 topic hz` 和 `ros2 interface show` 核实消息契约。
- 写一个简单 Action，练习反馈、取消和结果返回。

阶段验收：

- 能解释 Topic、Service、Action 和参数的区别。
- 能确认消息类型、频率、命名空间和 QoS。
- 能用 CLI 发现“有发布但没订阅”的问题。

### 阶段二：坐标、模型和可视化

目标：能编写一个含底盘、轮子、激光和 IMU 的 Xacro，并在 RViz2 中检查 TF。

验收：机器人模型与传感器 frame 位置正确，`tf2_echo` 能按时间查询，单位和轴方向有记录。

补充练习：

- 为底盘、激光和 IMU 补齐固定安装外参。
- 在 RViz2 中检查 `Fixed Frame`、机器人模型和激光点云是否一致。
- 用尺量、旋转和短距离直行验证坐标方向与尺度。

阶段验收：

- 能画出完整 TF 树，并说明每个 frame 的职责。
- 能区分静态 TF 和动态 TF。
- 能定位“模型对了但坐标错了”的原因。

### 阶段三：Gazebo 仿真闭环

目标：在仿真中驱动差速底盘，获得激光、IMU、编码器和 odom。

验收：直行和原地旋转误差可量化，传感器数据能在 rosbag2 中回放。

补充练习：

- 启动最小仿真闭环，只保留底盘、传感器和里程计。
- 比较命令速度、实际速度和反馈速度。
- 故意拔掉一个传感器，观察系统是否进入预期降级状态。

阶段验收：

- 能用 bag 回放复现一次仿真运动。
- 能量化仿真误差，而不是只说“看起来差不多”。
- 能把仿真问题和真机差异分开描述。

### 阶段四：定位和 SLAM

目标：完成一张小型室内地图，并在已知地图中定位。

验收：记录地图版本、分辨率、起终点误差、回环效果和失败场景。

补充练习：

- 先做一张小地图，再做一次定位，不要一开始就追求大场景。
- 比较 `slam_toolbox` 和 `amcl` 的输入输出差异。
- 记录定位丢失时系统的表现和恢复方式。

阶段验收：

- 能解释 `map`、`odom` 和 `base_link` 的关系。
- 能说明地图质量、里程计质量和时间同步对定位的影响。
- 能用失败场景证明定位链路是否稳定。

### 阶段五：Nav2 导航

目标：完成单目标、多个航点、动态障碍和恢复行为。

验收：明确成功率、平均到达时间、最小障碍距离、停止距离和恢复次数。

补充练习：

- 先跑通单目标导航，再增加航点和恢复行为。
- 在静态障碍和动态障碍场景下分别验证行为。
- 记录不同参数下的到达时间、成功率和最近障碍距离。

阶段验收：

- 能看懂 Nav2 的生命周期和行为树入口。
- 能判断问题来自地图、定位、代价地图还是控制器。
- 能解释为什么导航失败不一定是规划器本身的问题。

### 阶段六：工程化与真机迁移

目标：统一仿真和真机接口，增加诊断、日志、看门狗、急停和回归测试。

验收：传感器拔除、网络断开、定位丢失、控制器停止和低电量等场景都能进入预期安全状态。

补充练习：

- 给真机和仿真使用同一套 launch 入口，只通过参数切换环境。
- 给关键节点补上诊断、日志和健康检查。
- 设计一次升级和一次回滚演练，记录结果。

阶段验收：

- 能在不改业务逻辑的前提下切换仿真与真机。
- 能在故障时让系统进入明确的安全状态。
- 能用文档、bag 和日志复现实验结果。

### 学习节奏建议

比较稳妥的学习节奏是每个阶段至少完成一次“实现 + 故障 + 复现 + 记录”闭环：

1. 先做最小功能，确认系统真的跑起来。
2. 再故意制造一个错误，看看能否定位。
3. 再修复并录下验证证据。
4. 最后把过程写进 README 或实验记录。

如果时间有限，优先顺序建议是：通信 > 坐标 > 仿真 > 定位 > 导航 > 工程化。前面的基础没稳住，后面的内容会不断返工。

## 18. 项目验收模板

每个机器人项目都建议建立如下记录：

```text
项目名称：
硬件版本：
ROS 2 发行版：
代码提交号：
模型版本：
地图版本：
参数文件：

目标场景：
输入传感器：
核心 Topic：
TF 树：
控制频率：
速度/加速度限制：

成功指标：
失败指标：
安全策略：
复现命令：
rosbag 文件：
已知限制：
```

### 18.1 模板怎么用

这个模板不是交差清单，而是项目交付的最小证据包。建议在以下时点填写：

- 项目立项时，先填版本、场景和目标。
- 每次关键变更后，补充参数、地图、模型和代码提交号。
- 每次验收前，填写复现命令、bag 文件和已知限制。
- 每次上线后，记录实际结果和偏差。

如果一个字段暂时不知道，就不要空着不管，至少写明“待确认”以及后续确认方式。验收模板的价值在于把不确定性显式化。

### 18.2 验收流程

建议按固定顺序验收，避免只看最后结果：

1. **版本确认**：确认代码、参数、地图、模型和固件版本一致。
2. **最小运行**：先跑最小闭环，确认基础链路可用。
3. **场景测试**：在标准场景、边界场景和故障场景分别验证。
4. **证据采集**：保留 bag、日志、截图、录屏和关键命令。
5. **结果归档**：记录成功、失败和未覆盖项，并标出后续动作。

验收不应只看“能不能跑完”，还要看“失败时是否符合预期”和“以后能不能复现这次结果”。

### 18.3 证据要求

每次验收至少保留以下证据中的一部分，最好全部保留：

- `rosbag2` 数据。
- 关键节点日志。
- 配置文件和参数快照。
- 地图、模型和版本号。
- RViz2 或 Foxglove 截图。
- 复现命令和执行环境说明。

如果没有证据，验收结论就很难复查。机器人项目里最常见的问题不是“没测”，而是“测过但没法证明测过”。

### 18.4 签收标准

验收结果建议分成三类：

| 结果 | 含义 | 后续动作 |
|---|---|---|
| 通过 | 满足功能、性能、安全和复现要求 | 可以进入下一阶段或发布 |
| 有条件通过 | 只差少量非阻断问题 | 列出补齐项和截止时间 |
| 不通过 | 关键功能、稳定性或安全要求未满足 | 停止发布，回到问题定位 |

签收时至少要写清楚谁验证、何时验证、在哪个版本验证、用什么场景验证，以及是否存在保留问题。

### 18.5 建议的指标分类

推荐把验收指标分成四类：

1. **功能**：能否完成任务。
2. **性能**：延迟、频率、CPU、内存和成功率。
3. **精度**：位置、姿态、轨迹和目标误差。
4. **安全**：停止距离、失联行为、急停、限速和人工接管。

### 18.6 常见补充字段

如果项目偏工程交付，建议再补充这些字段：

- 部署环境：仿真、真机、工位或现场。
- 复现条件：是否需要特定地图、光照、地面或负载。
- 回滚方案：失败时如何恢复到上一个可用版本。
- 责任人：谁负责修复、谁负责复验、谁负责签收。
- 已知风险：哪些问题暂未修复但已接受。

这些字段能帮助后续维护，而不是只帮助一次性交作业。

## 19. 高频误区

第十九章把机器人学习和排障里最常见的误判集中列出来。它们的共同点不是“完全错误”，而是只看到了表面现象，却忽略了坐标、时间、接口、约束和证据链。

遇到这些问题时，优先做三件事：

- 先把现象写清楚，区分“看起来不对”和“实际上不对”。
- 先找最底层证据，比如 Topic、TF、bag、日志和版本。
- 先修复输入和契约，再调上层参数。

### 误区一：Topic 存在就说明通信正常

Topic 存在只说明名字能被找到，不说明消息真的能被正确消费。还要检查类型、Publisher/Subscriber 数量、QoS、频率、时间戳和消息内容。

常见表现：

- `ros2 topic list` 能看到，但下游节点没有反应。
- 消息频率看起来正常，但内容一直是空值或旧值。
- 发布端和订阅端类型不一致，或者 QoS 不兼容。

正确做法：

- 用 `ros2 topic info` 确认发布者和订阅者。
- 用 `ros2 topic echo` 看实际消息内容和时间戳。
- 用 `ros2 topic hz` 看频率是否稳定。
- 核对消息类型、命名空间和 QoS 配置。

### 误区二：TF 树能画出来就说明坐标正确

TF 可能连通但方向、原点、轴和时间都错误。应结合已知姿态、尺量距离和实际运动验证。

常见表现：

- RViz2 能显示模型，但机器人朝向和实际相反。
- 传感器点云看得到，但落点明显偏移。
- `map -> odom -> base_link` 全都有，但导航仍然发散。

正确做法：

- 用已知距离和已知旋转角做实测校验。
- 确认静态外参、轴方向和单位一致。
- 用时间查询验证 TF，而不是只看静态连通图。

### 误区三：调大参数就能解决导航失败

导航问题通常先来自底盘、里程计、传感器、footprint、地图或时间。算法参数必须在底层输入可信后再调。

常见表现：

- 轨迹绕圈、抖动、贴障碍或者穿墙。
- 规划器频繁重规划，但没有明显输入变化。
- 换一组参数“好像能跑”，但换个场景又坏掉。

正确做法：

- 先检查速度、加速度、TF 和 costmap 输入。
- 先确认地图分辨率、原点和 footprint。
- 再调规划器和控制器参数，且每次只改一类。

### 误区四：仿真跑通就能直接上真机

必须补充延迟、噪声、摩擦、饱和、故障、限速、急停和现场环境验证。

常见表现：

- 仿真中很稳，真机上抖动或偏航明显。
- 传感器和控制频率在真机上不一样。
- 仿真没有考虑硬件启动顺序、权限和网络问题。

正确做法：

- 对齐仿真和真机的接口与时间语义。
- 记录仿真与真机差异，显式加入噪声和延迟。
- 用录包回放和硬件在环补齐验证。

### 误区五：SLAM 可以替代所有定位和标定

SLAM 仍然依赖传感器质量、TF、里程计、时间和可观测环境。它不是错误输入的万能修复器。

常见表现：

- 以为开了 SLAM 就不用管里程计和外参。
- 地图漂移后试图只靠回环参数修复。
- 把定位失败直接归因为算法精度不足。

正确做法：

- 先保证传感器、TF、里程计和时间同步可信。
- 区分建图、定位和状态估计的职责。
- 用可观测场景和固定路线验证漂移来源。

### 误区六：安全只是最后加一个停止按钮

安全应从机械、电气、控制、软件、任务和运维全链路设计，普通应用逻辑不应成为唯一安全屏障。

常见表现：

- 认为软件里能停下来就已经“安全”。
- 把急停、限位和权限控制都交给普通业务节点。
- 出故障后靠手动重启来“恢复安全”。

正确做法：

- 把安全链路和业务逻辑分开设计。
- 为急停、超时、掉线和失联定义明确动作。
- 给恢复流程加权限、确认和日志。

### 误区七：节点越多就越模块化

模块化不等于碎片化。节点很多，只能说明拆得细，不说明职责清晰。

常见表现：

- 同一个功能被多个节点重复实现。
- 一个节点内部又塞进大量状态机、配置和调试逻辑。
- 故障一发生，排查路径比原来更长。

正确做法：

- 先按职责和数据流划分，再按部署需要拆分节点。
- 用包、接口和 launch 表达边界，不靠节点数量制造“整洁感”。

### 误区八：日志多就等于可观测

日志只是可观测性的一部分，不是全部。

常见表现：

- 日志很多，但问题发生时没有关键状态、频率或协方差信息。
- 只有报错，没有上下文、版本和关联 bag。
- 运行中能看到信息，但事后无法复现。

正确做法：

- 日志、诊断和指标分开设计。
- 给关键事件加版本、时间、上下文和关联 ID。
- 结合 bag 和截图形成完整证据链。

### 误区九：验收通过一次就永远通过

机器人系统的行为会随版本、参数、地图、环境和硬件状态变化。

常见表现：

- 只在第一次演示时认真验证，后续改动不再回归。
- 地图、参数和固件更新后，没有重新验收。
- 出现新问题时无法判断是回归还是新故障。

正确做法：

- 把验收变成持续流程，而不是一次性动作。
- 每次关键变更后都做最小回归。
- 保存版本和证据，便于比较前后差异。

## 结语

机器人学习的主线不是“记住更多算法名称”，而是逐步构建一个能解释、能观测、能复现、能降级的闭环系统：模型正确，坐标一致，时间可信，传感器可用，状态估计稳定，规划满足运动学约束，控制真正执行，仿真和真机差异可量化，故障和安全边界明确。

当一个机器人项目出现问题时，优先回到这条链路逐层验证，而不是直接复制新的参数或更换算法。能从 `/cmd_vel` 一直追到电机，再从传感器追到地图和目标，并且能用 rosbag2、RViz2、Foxglove 和日志复现问题，才算真正掌握机器人系统工程。
